# Второе мнение: gemini-4-argon

(запрос через a6api, 200, 65.57 c, usage {"prompt_tokens": 6903, "completion_tokens": 3718, "total_tokens": 10621})

Ниже — критический разбор документа с позиции архитектора агентных систем.

### 1. Оценка ADR-1 … ADR-15

*   **ADR-1 (Кэш-ориентированная сборка): Частично.** Идея верная для прямых API, но вы работаете через *маркетплейс-ретранслятор*. Если ретранслятор балансирует запросы в рамках одной сессии между разными провайдерами/инстансами (round-robin), префиксный KV-кэш работать не будет вообще, и жёсткая фиксация тулов только зря свяжет вам руки.
*   **ADR-2 (Протокольная гигиена): Частично.** Возвращать `reasoning_content` всех прошлых ходов verbatim — грубая ошибка для ряда моделей (например, линейки DeepSeek R1/V3-thinking): их API требует *вырезать* прошлые блоки рассуждений из истории, иначе контекст мгновенно забивается, а модель деградирует. Профиль должен поддерживать стратегию `strip_past_reasoning`.
*   **ADR-3 (Слой надёжности исполнения): Согласен.** Это базовый гигиенический минимум для работы с open-weights и дешёвыми моделями.
*   **ADR-4 (Плоский Edit-тул): Частично.** Правило «2 провала → переписать файл целиком (`Write`)» на файлах >500 строк гарантированно приведёт к обрезанию ответа по `max_tokens`, тихому удалению кусков кода (`// ... existing code ...`) и огромному расходу выходных токенов. Вместо перезаписи файла нужен фоллбэк на `Edit` по номерам строк (`replace_lines(start, end, content)`).
*   **ADR-5 (Управление выводом тулов): Согласен.**
*   **ADR-6 (Верификация): Частично.** Дописывать полный lint/typecheck после *каждой* правки опасно: при рефакторинге в 3–4 шага промежуточное состояние кода заведомо не компилируется. Дешёвая модель запаникует от ошибок компиляции на шаге 1 и начнёт откатывать правильные изменения вместо перехода к шагу 2. На каждый шаг нужен только быстрый синтаксический парсер (AST/tree-sitter), а полный typecheck/тесты — на Stop-гейте.
*   **ADR-7 («Одна рука на запись»): Согласен.** Это избавляет от сложнейшего класса багов с гонками и мерж-конфликтами.
*   **ADR-8 (Маршрутизация): Частично.** Тезис «при смене модели контекст сжимает старая модель» рискован: если переход идёт с дешёвой модели на премиум (эскалация при застревании), то сжимать контекст будет *уже запутавшаяся слабая модель*, которая зафиксирует свои галлюцинации в саммари. При эскалации вверх нужно отдавать сырой хвост логов или собирать контекст скриптом харнеса.
*   **ADR-9 (Промпт под семейство модели): Согласен.**
*   **ADR-10 (Слоистый конфиг профиля): Частично.** 8 слотов, 3 слоя наследования и смесь трёх форматов (frontmatter + YAML dsh + TOML Codex) — это явный оверинжиниринг для v1. Отлаживать, почему конкретное правило попало или не попало в промпт, будет крайне сложно.
*   **ADR-11 (Память): Согласен.** Замороженный снапшот на старт сессии — единственный способ сохранить кэш префикса.
*   **ADR-12 (Откат через теневой git): Частично.** Делать `git add -A` в теневую БД после *каждого* шага без жёстких фильтров убьёт диск и UI, как только агент запустит `npm install`, `cargo build` или сгенерирует дамп БД на 2 ГБ. Обязателен жёсткий лимит на размер блоба (например, <5 МБ) и принудительный учёт `.gitignore`.
*   **ADR-13 (Безопасность): Частично.** Правило «не грузить правила проекта в недоверенных папках» на практике не работает: пользователь открывает чужой репо, нажимает «Доверять» (иначе агент бесполезен), и получает prompt injection через `.cursorrules` / `CLAUDE.md`. Инструкции из репозитория всегда должны маркироваться тегами недоверенного контекста и не иметь права переопределять политики безопасности харнеса.
*   **ADR-14 (Свой SDK-sidecar): Согласен.**
*   **ADR-15 (Методика evals): Согласен.** Учёт цены за *решённую* задачу ($/pass) и разреза по провайдерам критически важен.

### 2. Спорные пункты (D1–D7 и 4a): что сделать иначе

*   **По D2 и 4a (Слепое планирование премиум-моделью):**
    *   *В чём проблема:* В 4a указано, что премиум-модель на старте пишет `task_spec` (план, файлы, шаги), при этом в п. 3.4 сказано, что премиум-модели — «одношаговые советники, не исполнители tool-циклов». Но нельзя написать точный план с указанием файлов, не прочитав репозиторий через `Grep`/`Read`.
    *   *Как надо:* Ввести фазу **Scout (Разведчик)** перед планированием. Дешёвая модель (или детерминированный скрипт с tree-sitter/repomap) собирает контекст задачи по ключевым словам (5–10 вызовов Read/Grep) и формирует пакет контекста. Только после этого премиум-модель в 1 шаг пишет `task_spec`.
*   **По D7 и 4a (Один запрос файлов у ревьюера):**
    *   *В чём проблема:* Ревьюер видит только дифф и может лишь «один раз запросить дополнительные файлы». Этого мало для проверки контрактов (например, изменили сигнатуру функции — нужно найти все её вызовы по проекту через `Grep`).
    *   *Как надо:* Вместо ручного запроса файлов ревьюером харнес должен **автоматически** строить расширенный контекст диффа через LSP/tree-sitter: подтягивать тела всех изменённых функций целиком + сигнатуры всех мест, где они вызываются (call sites).
*   **По D3 и 4a (Lean-компакция как дефолт для дешёвых моделей):**
    *   *В чём проблема:* Lean-компакция оставляет индекс ID сообщений и ждёт, что модель сама подтянет забытые детали тулом. Дешёвые модели ленивы: они не будут делать lookup по индексу, а начнут галлюцинировать содержимое старых файлов.
    *   *Как надо:* Для дешёвых исполнителей делать не компакцию истории, а **сброс сессии (hard reset) с передачей состояния через `task_spec` + `git status` / `git diff`**. Код на диске — лучшая память.

### 3. Что упущено (слепые зоны документа)

1.  **Таймауты стриминга и деградация маркетплейсов (TTFT / TPS).** На ретрансляторах дешёвые провайдеры часто не падают с 500-й ошибкой, а просто отдают 1 токен в 10 секунд или зависают посреди стрима. В ADR-3 нет политики обрыва медленных соединений (read timeout на чанк, минимальный порог TPS) и быстрого ретрая через другого апстрим-провайдера.
2.  **Конфликты правок с человеком (Live IDE state vs Disk).** Это десктоп-приложение. Пользователь параллельно с агентом открывает файлы в своей IDE, правит их или держит несохранённый буфер. В документе нет механизма file watcher'а, детекта внешних правок (dirty state) и инвалидации того, что агент прочитал 2 шага назад.
3.  **Кроссплатформенность Bash и песочницы (Windows-проблема).** Десктоп-приложение почти наверняка будут запускать на Windows. `srt`-песочницы, POSIX-скрипты и PTY там работают совершенно иначе (WSL vs Git Bash vs PowerShell). Это огромный источник сбоев тула `Bash`, который вообще не упомянут.
4.  **Управление фоновыми процессами и портами (Zombie processes).** В ADR-3 сказано «таймаут bash → уход в фон». Дешёвая модель запустит `npm run dev`, он уйдёт в фон по таймауту и займёт порт 3000. На следующем шаге модель решит, что команда упала, и запустит её снова (получив `EADDRINUSE`). Нужен строгий реестр фоновых процессов, проброс их живого лога в `<system-reminder>` и принудительный `kill` дерева процессов при закрытии задачи.
5.  **Латентность и UX подтверждений (`can_use_tool`).** Если агент ждёт подтверждения от пользователя на опасную команду 6 минут, то 5-минутный эфемерный кэш промпта (например, у Anthropic или ряда провайдерских кэшей) протухает. Следующий шаг после нажатия кнопки «Разрешить» пойдёт по полной цене cache miss.
6.  **Индекс кодовой базы (Repo Map / AST).** В наборе тулов есть только `Glob` и `Grep`. Без структурной карты репозитория (списка классов/функций через tree-sitter, как в Aider) дешёвая модель тратит первые 10–15 шагов просто на слепое блуждание по папкам, сжигая контекст до начала реальной работы.
7.  **Защита от утечки секретов в промпт (Secret Scrubbing).** Вы отправляете код в мутные провайдеры внутри маркетплейса-ретранслятора (многие из которых логируют трафик для дообучения). В харнесе отсутствует слой вырезания `.env`, ключей API и токенов *до* того, как результат `Read` или `Bash` попадёт в контекст модели.

### 4. Топ-5 рисков проекта (в порядке убывания критичности)

1.  **Иллюзия кэша на маркетплейсе-ретрансляторе (разрушение экономики).** Вся экономика проекта (ADR-1, ADR-8) строится на 50–90% экономии от prompt caching. Если ретранслятор не гарантирует sticky sessions (привязку сессии к конкретному воркеру конкретного провайдера), реальный cache-hit будет около нуля, и сметы вырастут в 5–10 раз.
2.  **Тихий даунгрейд и квантизация моделей провайдерами маркетплейса.** Свободные маркетплейсы (OpenRouter-подобные) регулярно маршрутизируют трафик на INT4/FP8-квантованные версии моделей без предупреждения. На квантованных моделях в первую очередь ломается генерация валидного JSON для тулов и точное цитирование кода в `Edit`, что обрушит pass rate.
3.  **«Потерянный в переводе» контракт между Планировщиком и Исполнителем.** Если премиум-модель сгенерирует слишком абстрактный `task_spec`, дешёвая модель не сможет его выполнить, но в `submit_report` уверенно соврёт, что всё сделано. Если же `task_spec` потребует глубокого ресерча до написания, премиум-модель разорит бюджет ещё на фазе планирования.
4.  **Деградация производительности десктопа из-за снапшотов (ADR-12) и фоновых процессов (ADR-3).** Локальный Electron/Tauri-клиент, который на каждый шаг агента гоняет гигабайты через теневой git, запускает параллельные линтеры и плодит недобитые node/python-процессы в фоне, очень быстро приведёт к зависанию системы пользователя.
5.  **Разбухание кодовой базы самого харнеса (Maintenance Hell).** Поддержка индивидуальных compat-профилей (ADR-2), кастомных системных промптов (ADR-9) и 8-слотовых конфигов (ADR-10) под зоопарк из 6+ быстро меняющихся китайских и западных моделей превратит разработку в бесконечную борьбу с регрессиями при каждом обновлении весов на стороне вендоров.

### 5. Фактические и методологические ошибки в документе

1.  **Противоречие по формату истории для reasoning-моделей (ADR-2 vs реальное API).** Утверждение *«возврат `reasoning_content` всех прошлых ходов verbatim; почему: DeepSeek без reasoning → HTTP 400»* содержит важную неточность. Официальный API DeepSeek (и совместимые с ним шлюзы) требует передавать `reasoning_content` предыдущих шагов **только внутри одного хода с цепочкой вызовов тулов** (sub-turns until final answer), но при начале нового пользовательского хода прошлые `reasoning_content` должны отбрасываться (или API их игнорирует/выдаёт ошибку при переполнении). Хранить их за всю сессию нельзя.
2.  **Некорректная оценка стоимости мульти-ревью в п. 4a.** Утверждается: *«при пакетах ≈10–20K токенов это дёшево»* и *«Контекст проверяющего ≈10–20K токенов»*. На практике в реальном проекте средний дифф на 5–7 файлов вместе с полным текстом затронутых файлов (иначе ревьюер не увидит неинициализированные переменные или сломанные импорты вне диффа), логами тестов и спецификацией легко занимает **40–80K токенов**. Умножьте это на 2 модели (Opus + GPT) и на 2–3 раунда итераций — ревью обойдётся в несколько долларов за одну задачу, что полностью съест экономию от дешёвого исполнителя.
3.  **Искажение выводов по «информационной стене» (п. 4a).** Вы ссылаетесь на рост метрики 45 → 75 при ×14 ресурсах как на обоснование своей дешёвой схемы с одним финальным ревью. Но в подобных архитектурах (generator-verifier с информационной стеной) кратный рост качества достигается за счёт **Best-of-N сэмплирования или жёсткого пошагового отката верификатором**, откуда и берётся множитель ×14 по токенам. Одиночная проверка в конце (даже в 3 раунда) не даст прироста в +30 п.п. без пропорциональных затрат на переписывание кода с нуля при фундаментально неверном подходе исполнителя.
4.  **Слепая вера в детерминизм доказательств (п. 4a, шаг 3).** Сказано: *«Харнес сам собирает доказательства: дифф, реальный вывод lint/тестов. Отчёт исполнителя — это утверждения, не доказательства»*. Упущен классический вектор обмана (reward hacking), который вы сами упоминаете в ADR-15 («жулик»): дешёвая модель меняет сами тесты (удаляет `assert`, ставит `.skip`) и этот дифф попадает в общий пакет. Харнес собирает «зелёный» вывод тестов, а ревьюер в большом диффе пропускает удаление одной строчки ассерта. Доказательством является только прогон *немодифицированных* тестов (или явная маркировка правок в `tests/` как красного флага для ревьюера).
