## 2. Консенсусные принципы → кандидаты в решения по ядру (ADR)

### ADR-1. Кэш-ориентированная сборка контекста [6/8]
Статичный системный промпт + фиксированный каталог тулов на всю сессию; всё динамическое (правила проекта, память, скиллы, окружение, время, смена режима) — дописывается в хвост (reminder/mid-convo system). Профиль, модель, `reasoning_effort`, thinking-режим и набор тулов фиксируются на сессию. Режимы (plan/review) — текстом/тулом, не изменением каталога. Компакция — реплей префикса байт-в-байт + инструкция последним сообщением.
*Почему:* попадание в кэш DeepSeek в 50× дешевле промаха; Claude Code: $11.20 → $1.62 за задачу при 90% hit; у DeepSeek тулы и effort рендерятся в начале промпта, у Kimi смена тулов/effort прямо «invalidates the KV cache». *Источники:* 02, 03, 04, 05, 01, 07.

### ADR-2. Протокольная гигиена и профиль совместимости модели [5/8]
Для каждой модели — явный compat-профиль: возврат `reasoning_content`/`<think>` всех прошлых ходов verbatim, неизменные `tool_call.id`, порядок tool results, явный `max_tokens`, запрет forced `tool_choice` в thinking, параметры семплинга по вендору (часто — не передавать), стабильный `user_id`. Pi за нашим URL получит дефолты «как OpenAI» — всё прописываем вручную.
*Почему:* DeepSeek без reasoning → HTTP 400; GLM 5.3 падает на `thinking:disabled` (который Pi шлёт по умолчанию в режиме zai без effort); Kimi через relay думает на `max` (×3 токенов). *Источники:* 07, 04, 05, 01.

### ADR-3. Слой надёжности исполнения [6/8]
Таймаут bash по умолчанию (+ уход в фон), ремонт/приведение аргументов по схеме, детектор «псевдовызовов» текстом, неисполнение вызовов из ответа, обрезанного по `length`, ≤2 повторов битого вызова с вычисткой мусора, детектор повторов/зацикливания, лимит шагов и бюджета.
*Почему:* в исследовании 34 прогона Pi зависли без таймаута; Cline: переход на нативные вызовы снизил ошибки DeepSeek V4 Flash 13.4% → 1.3%; Harness²: анти-псевдовызов дал 60 → 100. *Источники:* 08, 01, 02, 05, 06, 03.

### ADR-4. Edit-тул: плоский в стиле Claude Code + устойчивость [5/8]
`Edit(file_path, old_string, new_string, replace_all)`, Read с номерами строк, Write, Bash, Glob, Grep; fuzzy-поиск, сохранение BOM/CRLF, подсказывающие ошибки, «2 провала → переписать файл целиком», lint/typecheck в результате. Вложенный `edits[]` Pi — известная точка сбоев (модели шлют массив строкой). A/B против «bash + str_replace_editor» и apply_patch.
*Почему:* все вендоры оценивают и частично обучают модели в Claude Code; их собственные CLI сошлись к той же плоской схеме. *Источники:* 07, 02, 05, 03, 04.

### ADR-5. Управление выводом тулов [4/8]
Лимит inline (≈10–30K), сверх — файл + превью; при ошибке — начало и конец; заголовок с exit code / временем / исходным размером; неполное чтение помечается. *Источники:* 02, 03, 01, 05.

### ADR-6. Верификация — главный рычаг качества [6/8]
- После правки: lint/typecheck **дописываются в результат тула** («инструкцию модель может пропустить, строку в результате тула — нет», Harness²).
- Stop-гейт «тесты до зелёного» с капом продолжений; оценщик цели «готово / ещё нет / невозможно».
- Самопроверка дешёвой модели — детерминированно (тесты/скрипты); LLM-ревью — только от равной или более сильной модели.
- Ревью-пайплайн: находка → валидация → ≤3 раундов, повторно смотреть только новый дифф.
*Почему:* сильный ревьюит слабого +18.1 п.п., слабый сильного −8.6 п.п.; Claude Code: доля PR с содержательными замечаниями 16% → 54%; Harness²: verify-скрипт 43 → 78. *Источники:* 06, 02, 03, 05, 08, 04.

### ADR-7. «Одна рука на запись, много мнений» [3/8 + исследования]
Пишет один основной агент. Субагенты читают/исследуют/ревьюят. Премиум-модель — планировщик, ревьюер, советник со своим контекстом. Параллельных писателей нет (Boost — позже, только в изолированных worktree).
*Почему:* схема «премиум-лид + дешёвый помощник» $1.35 / 63.1 против $3.51 / 63.6 у Opus соло; делегирование суждений резко роняет качество. *Источники:* 08, 02, 05.

### ADR-8. Маршрутизация моделей — в харнесе, поставщики — в шлюзе [4/8]
Харнес (virtual models Pi) выбирает модель роли; переключение — только на старте сессии/подзадачи или на границе компакции; при смене модели контекст сжимает **старая** модель (Codex). Шлюз выбирает поставщика внутри модели, ведёт канарейки и рейтинг.
*Почему:* переключение вслепую к кэшу стоит 2.1–2.4× от «всё на флагмане», с учётом кэша — 0.19–0.28× (Factory, 2026-08). *Источники:* 08, 01, 03, 04.

### ADR-9. Промпт подбирается под семейство модели [4/8]
Для дешёвых — строгие правила workflow, точные описания тулов; для премиум — минимум (Anthropic вырезала >80% промпта для Claude 5 без потерь). Варианты внутри профиля, выбор — A/B на наших evals. *Источники:* 02, 08, 06, 01.

### ADR-10. Профиль = слоистый конфиг, фиксируемый на старте сессии [5/8]
Слои база → профиль → пользователь; роли могут сузить права, но не расширить. Состав профиля — 8 слотов Harness² с ценой и валидатором (лимит символов always-on, триггер у каждого скилла, проверка существования скриптов). Формат — смесь: frontmatter субагентов Claude Code + YAML-слои dsh + слои конфига Codex. Порядок предпочтения правок: скилл → скрипт → субагент → хук → постоянный текст («добавил — вырежи»). *Источники:* 06, 04, 03, 02, 05.

### ADR-11. Память [3/8]
Frozen snapshot в промпте, живое состояние — через результаты тулов; лимит в символах; «факты, а не инструкции»; фоновое ревью может только добавлять, изменения/удаления — в очередь подтверждения; журнал с откатом; куратор (устаревание/архив, без удаления). Эффект обучения на успех задач **не доказан** — включаем с измерением. *Источники:* 05, 03, 06.

### ADR-12. Откат файлов — снапшот всего рабочего дерева на каждый шаг [наше отличие]
Ни Pi, ни Claude Code, ни Codex, ни dsh полноценного отката не имеют (bash-изменения теряются). Берём дизайн OpenCode: отдельная git-БД объектов, снимок вокруг каждого шага, привязка к узлу дерева сессии. *Источники:* 01, 02, 03, 04 + OpenCode.

### ADR-13. Безопасность: детерминированное — первым слоем [5/8]
Песочница (srt), правила команд (как Starlark execpolicy Codex), защищённые пути, подтверждения внешних действий; LLM-классификатор — только дополнительный слой (guardrail-модели оставляют ~44% успешных атак). Граница доверия: правила проекта не грузятся в недоверенных папках; выход субагентов сканируется. Никакой отправки логов сессий на endpoint. *Источники:* 02, 03, 08, 05, 04.

### ADR-14. Протокол UI↔ядро — свой SDK-sidecar [4/8]
Модель событий Thread/Turn/Item (Codex app-server), подтверждения — запросы ядра к клиенту (`can_use_tool` с правкой входа и «запомнить правило»), steer с id текущего хода, генерация TS-типов. Свой sidecar на SDK Pi по образцу Graphone вместо стокового RPC (в RPC нет навигации по дереву). *Источники:* 03, 02, 01, 05.

### ADR-15. Методика evals [4/8]
Парные сравнения, ≥3 повтора, свежие приватные задачи, метрики: pass rate, **$ на решённую задачу**, cache-hit, пустые ходы; контрольные агенты (идеальный / ничего не делающий / жулик); отдельные замеры по каждому поставщику маркетплейса. *Почему:* разброс ±11 задач из 89 между повторами одной сборки; одна модель у разных провайдеров 74.2% vs 61.8%. *Источники:* 08, 05, 06, 02.

## 3. Что меняется в нашем плане

1. **Позиционирование.** Готовые харнесы почти не различаются по pass rate (±1–2 п.п.), зато по стоимости — до 40×; дешёвым моделям обвязка помогает сильнее (+10–15 п.п.), а настройка под модель (Harness²) даёт до +11.5. Обещание: «почти тот же результат в разы дешевле и стабильнее», а не «уровень Claude Code».
2. **Маршрутизация.** Модель роли выбирает харнес; шлюз — только поставщика. Переключения — на границах.
3. **Направление ревью.** Не «дешёвая проверяет код Opus», а наоборот; самопроверка дешёвой — тестами.
4. **Премиум-модели через ретранслятор — одношаговые советники/планировщики**, не исполнители длинных tool-циклов (рассуждения между шагами теряются при конвертации OpenAI → Claude/Gemini).
5. **Ядро.** Pi + свой SDK-sidecar (Graphone) + наши расширения. pi-desktop — вне окна свежести, только как пример моста.
6. **Edit-тул** — плоский в стиле Claude Code вместо `edits[]` Pi (A/B).
7. **Первые расширения** — пакет надёжности (ADR-3), профиль совместимости (ADR-2), снапшоты (ADR-12), верификация (ADR-6).
8. **Harness² — офлайн** для тюнинга профилей под модели; онлайн слишком дорог (5–7× токенов минимум).
9. **Цикл обучения памяти** — строим, но включаем по умолчанию только после evals.
10. **Шлюз** обязан пропускать reasoning-поля и usage-поля кэша; New API по умолчанию режет `preserve_thinking`, `tool_stream`, `prompt_cache_options`, `reasoning_details`.

## 4a. Решения по спорным пунктам (обсуждение 2026-10-22)

- **D1, D3, D4** — дефолты до экспериментов: богатый плоский набор тулов (правки всегда структурированным тулом — нужно UI для диффа/разрешений/снапшотов); lean-компакция + файл-якорь задачи (план и критерии приёмки переживают компакцию); плоский `Edit` с fuzzy и «2 провала → переписать файл». Окончательно — по B2, B3, B6.
- **D5 — принято:** смена профиля = новая сессия с передачей резюме, память общая; режимы внутри профиля — дописыванием в историю без смены тулов.
- **D7 — принято с правилом пользователя:** проверяет только агент, который **не выполнял** эту работу (другой экземпляр, другая модель, сила ≥ автора). Проверяющий не читает историю исполнителя — получает структурированный пакет (см. D2).
  - **Два мнения от разных семейств моделей на сложных и важных задачах** (деньги, архитектура и т.п.). Уровень риска `risk_level` (low / normal / high / critical) ставят: планировщик в `task_spec`, пользователь вручную, детерминированные триггеры харнеса (платёжный код, миграции БД, авторизация, инфраструктура, размер диффа). При high/critical:
    - на этапе плана — второй независимый план/мнение от премиум-модели другого семейства; расхождения показываются пользователю;
    - на этапе проверки — два независимых проверяющих разных семейств (например Opus 5.5 + GPT-5.6 или Gemini 4), не видят вердиктов друг друга;
    - сведение: находка у обоих → обязательна к исправлению; у одного → отдельная проверка находки; противоположные вердикты → решение за пользователем.
  - Основание: разные модели ловят разные ошибки (кросс-модельное ревью, arXiv 2607.21656); валидация каждой находки снижает шум (ревью-пайплайн Claude Code). Цена удваивается только на high/critical, при пакетах ≈10–20K токенов это дёшево.
- **D2 — гибрид остаётся гипотезой (проверка B4)**, уточнён структурированными контрактами между ролями:
  1. Планировщик (премиум) → `task_spec`: цель, проверяемые критерии приёмки, ограничения, файлы, шаги. Хранится файлом-якорем.
  2. Исполнитель (дешёвая) работает; в конце вызывает тул `submit_report` со строгой схемой: изменённые файлы, что и зачем, как закрыт каждый критерий, какие команды запускал, сомнения.
  3. Харнес **сам** собирает доказательства: дифф, реальный вывод lint/тестов. Отчёт исполнителя — это утверждения, не доказательства.
  4. Проверяющий (премиум, не автор) получает `task_spec` + дифф + доказательства + отчёт, **без транскрипта исполнителя**. Возвращает `review` по схеме: вердикт (approve / changes_requested / blocked), находки P0–P3 с `file:line`, нарушенный критерий, предложение. Может один раз запросить дополнительные файлы.
  5. Повторная проверка — только новый дифф + прошлые находки; максимум 3 раунда.
  Основания: «информационная стена» валидатора (Factory: Kimi K3 45 → 75, но ×14 ресурсов), классификатор auto mode не видит текст ассистента и результаты тулов, рубрика ревьюера Codex с JSON-схемой, diff-only повторное ревью Claude Code, «согласие ≠ доказательство» (Harness²). Контекст проверяющего ≈10–20K токенов вместо сотен тысяч, без «заражения» аргументами исполнителя.
- **D6 — гибрид «включено + выключено до evals»:**
  - Факты о пользователе и проекте (низкий риск): добавляются сами в пределах лимита, правки и удаления — в очередь подтверждения.
  - Процедуры/скиллы (высокий риск): «теневой режим» — агент предлагает, предложения копятся в панели как кандидаты и **не попадают в промпт**, пока пользователь не одобрит вручную; автоматическое включение кандидатов — только после того, как evals (B9) покажут пользу для данной модели и профиля.
