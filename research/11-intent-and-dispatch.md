# 11 — Слой намерений и диспетчер навыков/тулов/моделей (срез 2026-10-22)

Вопрос: как превратить расплывчатый запрос («сделай что-нибудь крутое, не знаю что и как») в хороший результат для обычного пользователя, и как не дать модели забыть установленные skills/плагины/MCP-тулы, не засоряя при этом контекст.

Обозначения:
- **[V] VERIFIED** — проверено по первоисточнику: код в клоне, текущая документация, arXiv (абстракт или полный текст).
- **[U] UNVERIFIED** — вторичный источник (обзор, агрегатор, форум, утечка промпта) или подтверждения в первоисточнике не нашлось.
- **[D]** — источник старше 2026-06-01. Приводится только с датой, когда на него опирается текущий источник или он задаёт метод измерения.

Связанные досье: `01-pi.md` (virtual models, exposure), `02-claude-code-anthropic.md` (skills, ToolSearch, кэш), `03-codex-openai.md` (skills 2%, BM25 tool_search), `05-hermes.md` (curator, tool_search), `08-practitioners-research.md` (роутинг Cursor/Factory), `00-synthesis.md` (ADR-1 кэш, ADR-7/8 роли и роутинг), `REPORT-2026-10-22.md` (цены и поведение моделей на нашем маркетплейсе).

## TL;DR (10 пунктов)

1. **Продукты сошлись на одной форме вопроса** [V]: одна карточка, **до 4 вопросов**, у каждого **2–4 готовых варианта**, первый помечен «рекомендуется», есть «Другое», и можно **пропустить → работа идёт с разумными умолчаниями**. Так делают Lovable (question card), Claude Code (`AskUserQuestion`), Hermes (`clarify`, первый вариант = Recommended) и Roast Room (≤4 вопросов или «just run it» с помеченными допущениями).
2. **Спрашивать полезно, но только когда надо, и лучше это решает отдельный «детектор неясности».** На SWE-bench с недоописанными задачами: без вопросов 54.8%, полностью описанная задача 70.8%. Отдельный intent-агент с вопросами даёт 69.4%. Один агент, которому разрешили спрашивать, — 61.2% (2603.26233, v3 от 2026-09-07) [V]. Kimi при этом спрашивает почти всегда (83–93% задач): дешёвые модели плохо откалиброваны.
3. **Переспрашивание вредит тихо**: на точности его не видно, оно проявляется на уровне сессии (усталость, брошенные задачи). Отсюда бюджет вопросов, «сделал допущение — скажи о нём» и дешёвая отмена (практики 2026-05 [D]; RegretBench 2026-07 [V]).
4. **Для обычного пользователя по умолчанию «сначала черновик, потом уточнение»**, а вопросы — для необратимых действий. Anthropic (2026-09-25): по расплывчатому запросу высокий effort выдаёт больше, но «делает больше допущений за вас». Низкий effort даёт быстрый старт для итераций [V].
5. **«Глубже, а не больше»** (skill be-ambitious, 2026-10-15 [V]) — четыре вопроса: что сделал бы топ-профессионал, с какого сырого материала он начал бы, какие методы и инструменты взял бы, **что кроме модели и пользователя докажет, что результат верный**. Прямых измерений эффекта на обычных пользователях нет. Это гипотеза для нашего эксперимента.
6. **Агенты изобретают велосипед, и pass rate этого не видит**: к 5-му ходу дублированная логика есть в 50.8% цепочек задач, а pass rate почти не меняется (RepoReuse, 2026-09-28 [V]). «Interface memory» (сводка уже созданных API) удваивает повторное использование своего кода: 30.0% → 67.8% [V].
7. **Выбор навыка деградирует с ростом каталога**: точность реального использования падает с 29.6% до 3.3% при росте пула с 5 до 100 skills (2608.14036 [V]). Haiku 4.5 опускается ниже 90% точности выбора тула уже на 10–15 тулах (2606.30317 [V]). Anthropic в документации называет порог 30–50 тулов [V].
8. **Рабочий рецепт диспетчера — двухступенчатый поиск по метаданным** (BM25/эмбеддинги → маленький reranker, top-3…5). Тело SKILL.md в индекс не класть: −3.2% (SkillSeek, 2026-09-30 [V]). Полный каталог в контексте почти бесполезен: 0.387 против 0.384 без skills при +59% токенов [V].
9. **Отложенная загрузка тулов работает и на дешёвых моделях** (Hermes, 288 прогонов, 2026-08-29 [V]): точность в пределах шума, токены −7…−23%. Одно исключение: **тул вопросов пользователю (`clarify`) нельзя прятать**, без него структурные вопросы падают с 18/18 до 7/18.
10. **Кэш-дисциплина**: весь «слой намерений» (классификация, вопросы, бриф, углубление, совет) работает **до** сборки основной сессии, отдельными вызовами. Сессия собирается один раз: профиль, модели, «горячие» skills и **неизменный** набор тулов. Всё новое дописывается в хвост: дельты индекса skills (как в Hermes), тела skills, найденные тулы через стабильный мост `tool_call`.

### 1.2. Паттерны, которые стоит взять

**P1. Два режима: «обсудить/спланировать» и «делать».** Он есть у всех: Lovable Plan/Build, Bolt Plan/Build, Replit Plan/Build, Cursor Plan/Agent, Claude Code plan mode. Для обычного пользователя режим не должен быть переключателем, который надо понимать. Его выбирает харнес по ясности и риску запроса (см. §6), а пользователь видит только кнопки «Поехали» / «Поправить» на карточке-брифе.

**P2. Карточка вопросов одной формы** [V, 4 независимые реализации]:
- одна карточка за раз, **≤4 вопросов** (Lovable 4, Claude Code 2–4 варианта, Hermes ≤5 вопросов и ≤4 вариантов, Roast Room ≤4);
- готовые варианты, первый — «рекомендуется»; «Другое» — свободный текст;
- **пропуск = продолжить с умолчаниями** (Lovable), **таймаут = продолжить** (Claude Code `askUserQuestionTimeout`, Replit take-over 10 мин, Jules auto-approve);
- для визуальных задач — **превью в вариантах** (HTML-мокап у Claude Code; цвет/шрифт/раскладка у Lovable).

**P3. Улучшатель промпта показывается как вопросы, а не как переписанный текст.** Bolt Enhance prompt сначала задаёт вопросы, потом выдаёт рекомендованный промпт, который можно править [V]. Для нашей аудитории переписанный промпт как текст бесполезен: пользователь не умеет его оценить. Ценность — в карточке вопросов и в брифе, а улучшенный промпт остаётся внутренним артефактом харнеса.

**P4. План/бриф простым языком с явными допущениями.** Lovable plan.md («key decisions, assumptions, and constraints»), Jules («assumptions or setup steps»), Roast Room («Mark every assumption as (assumed)», бриф ≤300 слов) [V]. Общий знаменатель: **что сделаю → что предположил → как проверю**.

**P5. Ранний дешёвый черновик или варианты.** Превью в вариантах ответа (Claude Code) [V], прототип за минуты (Replit [U]), несколько направлений (Stitch [U]). Anthropic, «Spending your effort» (2026-09-25) [V]: на запрос «build a personal fitness and workout tracker app» low effort за 1.5 мин дал «just a log and a simple graph», max за 67 мин — сложное приложение. Вывод автора: «higher effort levels will get more work done but Claude will also make more assumptions on my behalf». Для итераций лучше быстрый старт.

**P6. Прогрессивное уточнение после первого результата.** Чипы следующих шагов (Lovable), выбор элемента и рисование поверх превью (Lovable), «повтори с новыми фактами» (Roast Room) [V].

**P7. Прогресс и проверка, понятные неэксперту.** Таймлайн шагов (Lovable), **видеоповтор проверки** (Replit App Testing), «как я проверил» в итоге. Anthropic о дизайне (2026-09-22) [V]: без указаний Opus 5.5 скатывается к нескольким стилям по умолчанию, а «avoid a generic look» лишь меняет один шаблон на другой. Работает **список конкретных нежелательных приёмов**. Для Creative-профиля мы можем держать такой «анти-список» сами, чтобы пользователю не пришлось его писать.

**P8. Классификация намерения — отдельной дешёвой моделью и до основной работы.** Cursor Router (2026-08-06) [V]: Compass оценивает сложность хода, затем роутер по таксономии «domains × tasks × modifiers». Pi `jev-router.ts` [V]: классификатор отвечает на типизированный вопрос `complexity: standard|complex` с вероятностями, порог 0.5. Roast Room [V]: Chair по вопросу выбирает «сиденья» и веса 1–3.

### 2.2. Вывод для нас: политика «спросить / черновик / делать»

1. **Решение «спрашивать ли» принимает отдельный детектор, а не исполнитель** [V 2603.26233]. Для нас это шаг intake (§6), отдельный дешёвый вызов с JSON-ответом. Решение фиксирует детерминированная политика в харнесе, а не «настроение» модели (tianpan [U], Cursor «only route when performance is clearly better» [V]).
2. **Матрица ясность × риск**:
   - запрос ясен → делать сразу, одной строкой назвать допущения;
   - неясен, но обратим (черновик поста, дизайн, прототип, текст) → **черновик сначала** (2–3 быстрых варианта или один черновик с допущениями), потом уточнение. Это согласуется с «спросить после» для текстов [U] и с данными по effort [V];
   - неясен и необратим (рассылка клиентам, публикация, платёж, удаление, ответ покупателю на маркетплейсе) → **карточка вопросов**. Внешнее действие всё равно идёт через подтверждение (ADR-13).
3. **Бюджет**: один раунд, ≤3 вопросов в Daily/Creative, ≤4 в Code. Потом — коммит с помеченными допущениями.
4. **Форма**: только multiple-choice с рекомендованным первым вариантом, «Другое», «Не знаю — реши сам», кнопка «Просто сделай». Таймаут для низкого риска.
5. **Калибровка по модели**: Kimi склонен переспрашивать [V], у GLM один поставщик игнорирует системный промпт [V, REPORT]. Порог детектора подбираем по модели на нашем наборе (эксперимент E2).
6. **`clarify` всегда eager** [V Hermes]: тул вопросов нельзя прятать за tool_search.
7. **Вопросы строятся только из запроса пользователя и доверенного контекста.** Если вопрос возник из прочитанного письма или страницы, это помечается, а варианты, «подсказанные» внешним контентом, не делаются рекомендуемыми (риск ASPI [U]).

## 3. «Глубже, а не больше» и борьба с изобретением велосипеда

### 3.1. Техника be-ambitious [V]

`github.com/DannyMac180/skills/tree/main/be-ambitious` (merge 2026-10-15, клон проверен). Адаптация промпта Felix Rieseberg (Anthropic):

> «I want a deeper version of this task, not a bigger one. Before rewriting it: (1) say what a top professional in this field would do here that I'm not asking for; (2) name the rawest material they would start from instead of what has already been digested for me; (3) name the specific methods and tools they would use; (4) say what, other than you or me, would show the result is right. Then rewrite my prompt to ask for exactly that.»

Ключевые правила skill:
- сначала назвать область («SRE incident response», «clinical pharmacology»);
- **«Keep the user's goal and scope… Do not add deliverables, features, or side quests»** — защита от раздувания;
- внешняя проверка с критерием «что считается pass и fail»;
- «If you don't know… say so rather than inventing a source or tool»;
- после переписывания — стоп и предложение запустить.

Исходная рамка Rieseberg в пересказе (BestHub, 2026-10-15) [U]: **Altitude** (ставить цель-результат вместо шагов), **Depth** (экспертные инструменты, жёсткие целевые числа, сырые данные, «never let the model self-evaluate»), **Range** (команда специалистов, каждый со своими методами проверки, а не персоной). Там же критика: растёт нагрузка на проверку и копятся ранние ошибки. Ответ автора: «Ambition ≠ abdication».

**Как адаптировать для нашего пользователя.**
- Пользователь не видит переписанный промпт. Четыре вопроса — **внутренний шаг планировщика** (премиум-модель, один вызов).
- Наружу попадают только два пункта в брифе: «Возьму за основу …» (сырой материал или готовое решение) и «Проверю так: …» (внешняя проверка).
- Жёсткий scope-guard: углубление не может добавлять результатов. Число результатов в брифе после углубления ≤ числа до него (проверка детерминированная).

### 3.2. Есть ли доказательства, что переписывание и углубление помогают

- **TAPR** arXiv 2607.28657 (2026-07-17) [V абстракт]: маленький RL-обученный переписчик промптов даёт «consistent gains» на QA, суммаризации и GSM8K. Цифр в абстракте нет.
- **«Not All Queries Need Rewriting»** arXiv 2603.13301 (2026-03) [D][U]: переписывание помогает на одних наборах и вредит на других, сильная зависимость от домена.
- **Anthropic effort** (2026-09-25) [V]: с подробной спекой модели и уровни effort ведут себя гораздо ровнее. Цикл автора: «Give Claude a spec and ask it to interview me about any details I'm missing».
- **Прямых измерений «deeper-not-bigger» на обычных пользователях в 2026 не нашёл.** Это гипотеза. Проверяем в E6 с метрикой раздувания объёма.

**Техники для нас.**
1. **Шаг prior-art перед планом** (Code и Creative; в Daily — шаблоны и сервисы). Порядок поиска:
   1. установленные skills и коннекторы пользователя;
   2. наши шаблоны;
   3. библиотеки или пакеты;
   4. готовые сервисы.
   
   Результат попадает в бриф: «Возьму готовое X вместо написания с нуля».
2. **Проверка пакетов перед установкой** детерминированно, через API реестра: пакет существует, загрузки, возраст, лицензия, совпадение имени с известным. Без этого шаг prior-art увеличивает риск slopsquatting.
3. **Interface memory** в состоянии сессии [V эффект]: короткий реестр «что уже создано» (функции, компоненты, файлы, шаблоны). Он дописывается в хвост при сбросе или компакции.
4. **Ревьюер проверяет повторное использование**: «нет ли в репо или зависимостях готового аналога только что написанной функции». Это дёшево: grep плюс дешёвая модель.
5. **Выбор исполнителя для Code**: DeepSeek V4.1 Flash лидирует по повторному использованию в RepoReuse [V], при этом кэш у него через маркетплейс не работает [V REPORT]. Компромисс решаем измерением.

**Суть.** Чем больше skills и тулов видно сразу, тем реже модель выбирает правильный. Пустые и похожие друг на друга описания добавляют ложные срабатывания. Каталог целиком в контексте тратит токены и почти ничего не даёт. Работает отбор под задачу (top-3…5) плюс поиск по требованию.

**Паттерн «напоминание в нужный момент»** (TTSR, magic keywords, Hermes delta) — главный инструмент против «модель забыла про установленный навык» без раздувания префикса. Описание лежит в индексе, а напоминание о нём дописывается в хвост, когда сработал детерминированный триггер: слово в запросе, тип файла, вызов тула, ответ классификатора.

### 4.3. Дизайны роутеров и диспетчеров

**Модели.**
- **Pi virtual model / `jev-router.ts`** [V]. Планирование на сильной модели (Sol, если классификатор Jev дал `complex` ≥0.5, иначе Terra). **После первого успешного `edit`/`write` следующий запрос уходит на дешёвую Luna, и сессия там остаётся**: «switches models once and accepts a single prompt-cache miss». Фаза — состояние роутера на ветке сессии, переживает компакцию. В `route()` есть `reason` (`user` / `continuation` / `retry`), `previous`, `failed`, `state`. Для классификации у Pi есть **classifier models** (Jev, Cloudflare Clef, OpenAI GPT-6 Luna через Decisions API): типизированные вопросы `choice / bool / score` с вероятностями. Через наш маркетплейс их, скорее всего, нет [U]. Замена — дешёвая чат-модель с JSON-ответом.
- **oh-my-pi roles + prewalk** [V] — та же идея, конфигурацией.
- **Cursor Router** (2026-08-06) [V]. Пер-ходовой. Compass предсказывает, будет ли пользователь доволен ответом дешёвой модели. Сигнал качества: «Moving on to the next task is a strong positive signal, while correcting the agent is a strong negative one». В цене учитывает промахи кэша при смене модели. Переключение только при 75% уверенности в выигрыше. Auto Balance: −41% стоимости к Opus 4.8 при +3% удовлетворённости.
- **Factory Router** (2026-09-23) [V]: агрегированная экономия 42% → 63%, медиана по сессиям −72.5%, 99% pass rate Opus 4.7 на TB2. Factory (2026-08-24, досье 08) [V]: роутинг в харнесе, не в шлюзе; переключение вслепую к кэшу стоит 2.1–2.4× от «всё на флагмане».
- **OpenRouter Auto / Not Diamond** [U]: в 2026 сообщают о смене движка (сигнал по использованию сообществом), первоисточник не нашёл.

**Skills и тулы.**
- **Двухступенчатый поиск** (SkillSeek [V]): BGE-base bi-encoder → маленький cross-encoder, top-20 → top-5, на CPU, без LLM в цикле. Сравним с LLM-петлёй (Liu et al.) при половине цены ($27.54 против $51.30 за прогон). Индексировать **имя, описание и теги**, без тела.
- **SkillReranker** arXiv 2607.06283 (2026-07-07) [V абстракт]: разложить задачу на подзадачи и выбирать skills на каждую. Меньше шагов и токенов, цифр в абстракте нет.
- **«Forced-eval» хук** (Spence [D][V]): перед работой модель отмечает YES/NO по каждому skill из короткого списка. Даёт 100% активации на простых промптах. Подходит как второй этап после поиска, когда кандидатов 3–8, а не 100.
- **Community skill-routers** (charon-fan/agent-playbook 2026-06-21, borghei/claude-skills, zpankz/mcp-skillset, SkillForge) [U]: skill-маршрутизатор как отдельный skill с intent-анализом. Это промпт-роутер без кода и измерений. Не брать как основу.

### 4.4. Как измерять

**Набор данных (наш «Dispatch-set»).** 100–150 запросов по трём профилям:
- ~60% должны вызвать конкретный skill или тул (разметка: ожидаемый набор);
- ~20% не требуют ничего (проверка ложных срабатываний, как сценарий E «no_tool_needed» у Hermes);
- ~20% — «почти близнецы» и многошаговые (2 skills или тула подряд).

Каталоги размером 5 / 20 / 50 / 150 из реальных skills (anthropics/skills, bundled Hermes, наши) плюс намеренные дубли.

**Метрики.**

| Группа | Метрика | Откуда идея |
|---|---|---|
| Выбор | Recall@k шорт-листа; Hit@1 | SkillSeek, 2608.08453 |
| Загрузка | Precision/recall реальной загрузки (`skill_load` / `tool_search` вызван с правильным именем) | Claude plugin eval `tool_used`, Spence |
| Ложные срабатывания | Доля загрузок на запросах «ничего не нужно»; число ложных `tool_search` | Hermes сценарий E, Spence true negatives |
| Использование | **Actual-use precision**: загрузил и действительно следовал (судья по транскрипту) | 2608.14036 |
| Эффект | Δ успеха задачи против «без skills» (две ветки) | `claude plugin eval --ablation with-without` |
| Цена | Токены листинга на сессию; cache hit rate; лишние ходы на мост (Hermes: +1–2 хода); латентность | Hermes, Claude Code SLO |
| Онлайн | Доля «moved on» против «исправил агента»; skills, которые судья счёл нужными, а модель не загрузила (undertrigger); распределение использования | Cursor Router, Anthropic PreToolUse |

**Дисциплина** (из Hermes, [V]): ≥3 прогона на ячейку, ±3% на одном прогоне считаем шумом, упавший прогон = 0 и остаётся в знаменателе, спорные ячейки расширяем до n=6. В интерактивных задачах сценарный «пользователь» отвечает на вопросы, иначе задачи с уточнением несправедливо получают 0.

### 4.5. Телеметрия и чистка неиспользуемых skills

- **Hermes curator** [V]:
  - счётчики `view_count / use_count / patch_count / last_activity_at`;
  - детерминированно: не использовался 14 дней → `stale`, 30 дней → архив в `.archive/`; **никогда не удаляет**;
  - pinned и skills из cron-задач не трогаются; «use_count == 0 is absence of evidence», поэтому новые skills защищены периодом не меньше 14 дней;
  - LLM-консолидация «зонтиков» по умолчанию **выключена** (50–100 вызовов за проход);
  - встроенные skills архивируются только по opt-in (`prune_builtins`), skills из хаба — никогда.
- **Anthropic** (2026-06-03) [V]: лог PreToolUse по вызовам skills, чтобы находить популярные и недосрабатывающие.
- **Для нашей аудитории** — «полка навыков» без технических слов:
  - «Чем пользовались на этой неделе»;
  - «Ни разу не пригодились за месяц — убрать с полки?» (скрыть из индекса, не удалять);
  - «Закрепить»;
  - в брифе явная строчка «Использую ваш навык „Посты в Telegram“». Так забытые навыки возвращаются в поле зрения.
- **Линтер описаний** при установке [V основание 2608.08453]: шаблон «[Глагол] [что]. Используй, когда [триггер].», ≤250 символов. Предупреждение о «близнецах»: по эмбеддингам описаний, порог подбираем. Слабое описание переписывает дешёвая модель по шаблону, исходное сохраняется.

## 5. Roast Room — что взять, что не брать

**Что это** [V, клон `nateherkai/roast-room`, MIT, © 2026 AI Automation Society, коммит 2026-10-21]. Skill для Claude Code «совет директоров по одному бизнес-решению».
- Chair (основная сессия) ведёт процесс. 7 «сидений» по умолчанию и 5 «на вызов», каждое — сабагент с «мозгом» из публичных материалов реального человека (Bezos, Buffett, Hormozi…) и со своим «столпом» (стратегия, деньги, продажи и т.д.).
- 3 раунда: позиции → дебаты по cruxes → голосование по проекту резолюции. Взвешенные оценки, вердикт, PDF.
- Локальное веб-приложение «комната» проигрывает файлы сессии (портреты говорят, летят стрелки) и **само не делает AI-вызовов**.
- Полный совет — 3 прогона на сиденье, 21 сабагент, «about 1M tokens». Режим `--quick`: 4 сиденья, 2 раунда.

### 5.1. Что переиспользовать (механики, не персоны)

| Механика | Как в Roast Room | Зачем нам |
|---|---|---|
| **Сборщик брифа** | Решение одной строкой; варианты A/B/C, **всегда с «не делать / оставить как есть» и меньшей версией идеи**; бизнес, ресурсы, критерий успеха, **куда склоняется пользователь** («the council tests the lean, it does not echo it»). Не хватает фактов → ≤4 вопроса одной карточкой; «just run it» → допущения с пометкой `(assumed)`; бриф ≤300 слов | Готовый шаблон брифа для Daily |
| **Выбор состава** | Chair рекомендует 5–7 сидений с причиной в одну строку. Режимы `ask / auto / default` | Для нас по умолчанию `auto` с объяснением в одну строку |
| **Обязательные сиденья** | «One seat that guards the downside» + «the seat most likely to disagree» | Встроенная защита от поддакивания |
| **Веса 1–3** | Ровно 1–2 сиденья с весом 3, остальные ≥1 | Честная агрегация |
| **Cruxes** | После раунда 1 Chair выписывает 1–3 корня разногласий (факт, числа, ценности) и кто на какой стороне | Понятная пользователю структура спора |
| **Тревога единогласия** | Единогласный раунд 1 = «warning, not a win»: Chair назначает сильнейшую неаргументированную альтернативу и сиденья, которые обязаны её защищать | Против ложного консенсуса |
| **Оверрайды** | **Ruin cap**: одно сиденье с «RUIN RISK: likely» ограничивает вердикт уровнем RESHAPE. **One-way door cap** при разбросе ≥4 | Осторожность в необратимом |
| **Формат вердикта** | Полосы GO ≥7.5 / GO WITH CONDITIONS / RESHAPE / DON'T DO IT, плюс WAIT с триггером и датой. Разброс и уверенность. **Cheapest test, kill criteria, revisit**. Мнение меньшинства. Чат-версия ≤200 слов | Карточка решения, понятная за 15 секунд |
| **Chair не спорит** | «You never argue a side»; важный пропущенный довод отдаётся ближайшему сиденью как crux | Разделение ролей, премиум-модель как Chair |
| **Проверка цитат** | Скрипт: каждая цитата с source id должна дословно найтись в «мозге»; непроверенные удаляются | Для нас: **проверка чисел и фактов** — каждое число в вердикте взято из брифа или помечено как допущение |
| **Комната из файлов** | UI читает `council.json / cruxes.json / round-N.md / verdict.json`, модель пишет файлы | Наш «живой прогресс»: UI подписан на события, без лишних вызовов модели |
| **Без сабагентов** | Последовательно, «clear your head before the next seat» | Fallback для дешёвого режима |

### 5.2. Что не брать и риски

- **Реальные люди как персоны и портреты из их фото** (через kie.ai). Это риск имитации и ложной аффилиации, право на образ, и обычный пользователь легко примет «так сказал Баффет» за настоящий совет. Дисклеймер в README этого не снимает. **Берём только обобщённые роли.**
- **«Мозги» из скрапинга YouTube и эссе** — авторские права и ToS. Наши роли описываются методами («юнит-экономика», «обратимость решения», «проверка спроса»), без цитат людей.
- **Финансовые и юридические советы.** Нужна роль-осторожность, которая только **флагует** риски, и явная пометка «это не консультация юриста/финансиста».
- **Поддакивание в дебатах — главный известный провал.** ACL 2026 «When Identity Skews Debate» [V абстракт]: «sycophancy far more common than self-bias», анонимизация идентичностей снижает смещение. Отсюда: в раунде 2 показывать карточки без указания, чья своя; брать **разные семейства моделей** на сиденья. Ранняя работа (arXiv 2509.23055 [D]) показывает, что дебаты часто не лучше одиночного агента. Нужен эксперимент E7 против «одна сильная модель + self-consistency».
- **Цена.** У Roast Room ~1M токенов на полный совет. У нас на дешёвых моделях это $0.001–0.2 за совет (цены из REPORT). Деньги не проблема, проблемы — время (21 вызов) и внимание пользователя. По умолчанию быстрый режим.

### 5.3. Предложение: «Совет» в профиле Daily

- **Триггер**: intake классифицирует запрос как «решение» («стоит ли», «что выбрать», цена, найм, запуск) → в брифе кнопка «Собрать совет».
- **Роли** (обобщённые, без имён и лиц, абстрактные аватары):
  - «Финансист» (деньги и риск разорения — обязательное downside-сиденье);
  - «Голос клиента» (спрос);
  - «Продажи и маркетинг»;
  - «Операционщик» (время и процессы);
  - «Адвокат дьявола» (обязательное dissent-сиденье);
  - «Осторожность» (юр. и репутационные флаги);
  - «Стратег» (обратимость).
- **Быстрый совет**: 4 сиденья × 2 раунда, дешёвые модели разных семейств. Chair на премиум-модели. Раунд 3 только при разбросе >3 или «риске разорения».
- **Вывод**: карточка «Вердикт / почему / главный спор / самый дешёвый тест / когда остановиться». Комната как анимация прогресса из событий.
- **Тот же механизм в Code и Creative**: «мульти-ревью» (безопасность, UX, производительность, «а есть ли готовое»). Это согласуется с ADR-7 «одна рука на запись, много мнений».

## 6. Предлагаемый дизайн: «слой намерений» + «диспетчер»

### 6.1. Принципы

1. **Всё, что решает «что и как делать», происходит до сборки основной сессии**, отдельными короткими вызовами со своими стабильными префиксами. Основная сессия собирается **один раз** и не меняет системный промпт, набор тулов, модель исполнителя и effort (ADR-1).
2. **Решения «спросить / черновик / делать» и выбор skills принимает политика харнеса** на основе ответов дешёвых классификаторов, а не исполнитель «по ходу».
3. **Пользователь видит три вещи**: карточку вопросов (иногда), карточку-бриф (всегда, иногда с автостартом), понятный прогресс и «как я проверил».
4. **Видимость навыков дозирована**: 3–5 «горячих» skills полностью, остальные по имени или через поиск. Напоминания в нужный момент вместо постоянного присутствия.

### 6.3. Схема `Intent` (ответ intake)

```json
{
  "profile": "daily | code | creative",
  "task_kind": "make_new | change_existing | answer | decide | automate | communicate",
  "clarity": 0.0,
  "stakes": {"external_action": true, "money": false, "irreversible": true, "audience": "clients"},
  "size": "minutes | hour | multi_hour",
  "deliverables": ["пост в Telegram"],
  "missing": [{"slot": "тон", "why": "меняет результат", "default": "дружелюбный", "options": ["дружелюбный", "экспертный", "с юмором"]}],
  "skill_candidates": ["telegram-post", "image-gen"],
  "connectors_needed": ["telegram"],
  "decision_like": false,
  "language": "ru"
}
```

`missing[].default` обязателен: без него нельзя сделать «Просто сделай». `deliverables` нужен для проверки scope-guard после углубления.

### 6.4. Пример брифа (что видит пользователь)

> **Запрос:** «сделай что-нибудь крутое для моего канала про кофе»
>
> **Что сделаю:** серию из 3 постов на неделю + 1 картинку к первому.
> **Что я предположил** *(можно поменять)*: тон дружелюбный · аудитория — любители кофе дома · без рекламы.
> **Чего не буду делать:** публиковать без вашего «ок».
> **Использую ваши навыки:** «Посты в Telegram», «Картинки для постов».
> **Как проверю:** длина и ссылки, превью картинки в формате Telegram, нет повторов с вашими последними 20 постами.
> **≈ 2 минуты, < 1 цента.**
> [Поехали] [Поправить] *(старт через 15 с)*

### 6.5. Диспетчер моделей (роли)

| Роль | Когда | Модель (по REPORT, цены за 1M вход/выход) | Почему |
|---|---|---|---|
| intake / классификатор / вопросы | Шаги 0–2 | DeepSeek V4.1 Flash ($0.0012/$0.0048) или Qwen flash | Короткие вызовы, кэш не важен. Нужен надёжный JSON |
| черновик / варианты | Шаг 2' | Дешёвая, low effort | Быстрый старт [V effort] |
| планировщик / углубление / Chair | Шаги 3, совет | Opus 5.5 ($0.096/$0.48) или GPT-6.1 | Суждение, prior art, критерии проверки. Один вызов |
| исполнитель | Шаг 6 | GLM-5.3 / MiniMax M3 / Kimi K3 / DeepSeek — по eval и кэшу | Основной объём токенов; кэш через маркетплейс: MiniMax ~80%, GLM ~50%, Kimi ~30%, DeepSeek 0–2% [V REPORT] |

### 6.6. Чек-лист кэш-дисциплины

- [ ] Шаги 0–4 и совет — **вне** основной сессии, со своими неизменными шаблонами.
- [ ] Системный промпт сессии без таймстемпов. Порядок skills и тулов детерминирован (сортировка по имени).
- [ ] Набор тулов профиля не меняется до конца сессии. **Pi `tool_search` по умолчанию «declares the matches for the next model call»**, то есть меняет массив tools. У DeepSeek и Kimi тулы рендерятся в начале промпта, смена тулов инвалидирует кэш [V, ADR-1]. Поэтому для MCP и редких тулов мы используем **стабильный мост `tool_call(name,args)`** (как в Hermes) или codemode (описание стабильно). Выбор — по E4.
- [ ] Изменения каталога skills → дельта-заметка в хвост (Hermes), а не пересборка промпта.
- [ ] Тело skill → tool result или user message (как в Claude Code / Pi).
- [ ] Напоминания → скрытые сообщения в хвост, на один ход.
- [ ] `clarify` eager, всегда в наборе.
- [ ] Пересборка префикса только на компакции или «сбросе с передачей состояния» (REPORT). Бриф, interface memory и список загруженных skills переносятся в новый хвост.
- [ ] Поставщик закреплён за сессией (REPORT, H1).

### 6.7. Открытые вопросы и риски

- **Ложная уверенность intake.** Классификатор назвал запрос ясным, а он нет. Смягчение: бриф показывается всегда, кнопка «Поправить», допущения на виду.
- **Автостарт по таймеру** допустим только для обратимых действий без внешних эффектов.
- **Галлюцинации пакетов при prior art** — только с проверкой в реестре.
- **Вредные skills** (dependency steering [U]): skills из недоверенных источников проходят сканер и не попадают в «горячие» без явного согласия.
- **Пользователь не читает бриф.** Делаем его в 5–7 строк, а главное — «что предположил» и «чего не буду делать».

Ветки: все 40 сразу / ядро 8 + мост / ядро + Pi `tool_search` / codemode. Модели: GLM, MiniMax, Kimi (у них кэш работает) + DeepSeek. 3 прогона. Отдельно: `clarify` eager против deferred на «ловушке» с неоднозначным удалением | Успех, неверный тул или аргументы, лишние ходы, **cached_tokens из usage**, $ | ~70M токенов → **~$1.5** |
| **E5. Шаг prior-art** | Явный шаг «поищи готовое + проверь пакет в реестре» уменьшает объём своего кода и не добавляет выдуманных пакетов | 20 задач, где есть очевидная библиотека (даты, CSV, QR, Markdown → HTML, парсинг RSS, ресайз картинок…). Ветки: без шага / с шагом / с шагом + проверка реестра. DeepSeek и Qwen × 3 прогона | Строк своего кода, число и «реальность» зависимостей (PyPI/npm JSON API), тесты | ~15M → **~$0.4** |
| **E6. «Глубже, а не больше»** | Скрытое углубление по be-ambitious повышает качество без роста объёма; обычный «улучшатель промпта» объём раздувает | 30 задач трёх профилей. Ветки: сырой запрос / «enhance prompt» (переписать подробнее) / be-ambitious (4 вопроса, scope-guard). Планировщик Opus, исполнитель GLM. Судьи вслепую | Качество (попарно), **число результатов против запроса** (раздувание), наличие внешней проверки, $ | ~$0.6 |
| **E7. Совет против одиночного ответа** | Быстрый совет (4 обобщённых роли, разные семейства, премиум-Chair) лучше одиночной дешёвой модели и не хуже одной премиум-модели с self-consistency; анонимизация в раунде 2 снижает поддакивание | 12 бизнес-решений с рубрикой. Ветки: дешёвая одна / премиум одна (×3 + голосование) / совет / совет с анонимизацией. Проба поддакивания: в бриф вписан заведомо слабый «наклон» пользователя | Попарная оценка двумя судьями, доля ответов, принявших слабый наклон, разброс, время | ~$1.0 |
| **E8. Линтер описаний** | Переписывание описаний по шаблону «[Глагол] [что]. Используй, когда …» ≤250 символов поднимает Hit@1 и снижает ложные срабатывания | Повтор подмножества E3 (каталог 50 и 150) с исходными и переписанными описаниями | ΔHit@1, Δложных | ~$0.3 |
| **Резерв** | Повторы спорных ячеек до n=6, канарейки, отладка | — | — | **~$4** |
| **Итого** | | | | **≈ $6 + резерв $4 ≤ $10** |
