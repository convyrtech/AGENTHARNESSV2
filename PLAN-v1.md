# План v1: универсальный агентный харнес для казуальных пользователей

Последнее обновление: 2026-10-22. Это рабочий документ: после каждого этапа исследований и экспериментов он уточняется. Подтверждённые факты и открытые гипотезы ведутся в `STATUS.md`.

---

## 1. Продукт и цель

**Что строим.** Десктопное приложение (Tauri 2 + React, Windows/macOS/Linux) с агентом, который работает с локальными файлами, кодом и сервисами пользователя. Внутри — переключаемые профили: «Код», «Повседнев», «Творчество».

**Для кого.** Казуальные пользователи. Они не знают и не хотят знать, как это устроено, не умеют писать промпты и формулировать задачи. Типичный запрос: «сделай пиздато то, не знаю что, не знаю как». Пользователь додумывает по ходу и не собирает референсы заранее.

**Модель бизнеса.** Клиент бесплатный, работает только через ключи нашего сервиса. Сервис перепродаёт модели с маркетплейса a6api (решение владельца: только маркетплейс). Ценность для пользователя:
- дешёвый доступ к моделям без VPN;
- харнес, который выжимает максимум из дешёвых моделей;
- современное и удобное приложение.

**Главное обещание (после исследований):** не «уровень Claude Code на дешёвых моделях», а **«почти тот же результат в разы дешевле, стабильнее и без умения писать промпты»**. Независимые данные показывают, что готовые харнесы почти не различаются по доле решённых задач (±1–2 п.п.), зато сильно различаются по стоимости (до 40×). Дешёвым моделям обвязка помогает сильнее всего (+10–15 п.п.).

## 2. Архитектура (верхний уровень)

```
┌────────────── Десктоп (Tauri 2) ───────────────┐
│ React UI: чат · план простыми словами ·        │
│   превью · дифф · дерево сессий · память ·     │
│   «комната» агентов · стоимость                │
│ Rust-мост: снапшоты файлов, keychain,          │
│   индекс памяти (SQLite FTS5 + sqlite-vec)     │
│ Sidecar: Pi SDK (по образцу Graphone) +        │
│   наши пакеты расширений                       │
└───────────────────────┬────────────────────────┘
                        │ OpenAI-формат
┌───────────────────────▼────────────────────────┐
│ Наш шлюз: авторизация · биллинг · закрепление  │
│ поставщика за сессией · канарейки · рейтинг    │
│ поставщиков · детектор «ответов-ошибок» ·      │
│ вычистка секретов                              │
└───────────────────────┬────────────────────────┘
                        ▼
                a6api (маркетплейс)
```

**Ядро — Pi** (earendil-works/pi, MIT, v1.4): минимальный цикл, виртуальные модели для ролей, расширения, пакеты, дерево сессий.
- DeepSeek обучал V4.1 в том числе на Pi.
- Стоковый RPC в прод не берём: в нём нет навигации по дереву. Делаем свой sidecar на SDK.
- Между UI и ядром — тонкий адаптер, чтобы ядро можно было заменить (OpenClaw в итоге ушёл с ядра Pi).

## 3. Принципы ядра (ADR, подробно в `research/00-synthesis.md`)

1. **Кэш-ориентированный контекст.** Статичный промпт и набор тулов на сессию. Всё динамическое дописывается в хвост. Профиль, модель и effort фиксируются на сессию. Режимы переключаются текстом, без смены тулов.
2. **Профиль совместимости каждой модели и каждого поставщика.** Поля рассуждений, формат thinking, семплинг, `tool_choice`. Pi за нашим URL сам ничего не определит.
3. **Слой надёжности:**
   - таймауты bash и стрима;
   - починка аргументов;
   - детектор псевдовызовов и зацикливания;
   - лимит шагов и денежный лимит на задачу;
   - повторы по типу тула (повторять только безопасные);
   - реестр фоновых процессов и портов.
4. **Плоский `Edit`** в стиле Claude Code. Нечёткое совпадение — только с показом применённого фрагмента. Для больших файлов — правка по диапазону строк.
5. **Управление выводом тулов:** лимит, файл + превью, начало и конец при ошибке.
6. **Проверка — главный рычаг:**
   - быстрый синтаксис после правки;
   - тесты на внешнем стоп-гейте («до зелёного», с лимитом);
   - тесты только для чтения;
   - доказательства собирает харнес.
7. **Одна модель пишет, остальные читают и советуют.**
8. **Модель для роли выбирает харнес, поставщика выбирает шлюз.** Переключение модели — только на границах подзадач.
9. **Промпт по классу модели.** Топам — абстрактная цель и «копни глубже». Дешёвым — чёткий регламент.
10. **Профиль — слоистый конфиг (база → профиль → пользователь).** В v1 3–4 слота: промпт, тулы и скиллы, роли моделей, политика.
11. **Память** — см. раздел 6.
12. **Откат всего рабочего дерева на каждый шаг** (дизайн снапшотов OpenCode, с учётом `.gitignore` и лимитом размера). Это наше отличие от конкурентов.
13. **Безопасность:**
    - сначала детерминированные меры: песочница, правила команд, подтверждения;
    - инструкции из репозитория всегда недоверенные;
    - вычистка секретов до отправки.
14. **Протокол UI ↔ ядро по образцу Codex app-server:** Thread/Turn/Item, подтверждения как запросы ядра к клиенту.
15. **Evals:** парные сравнения, стоимость на решённую задачу, канарейки поставщиков.

## 4. Для казуалов: «слой намерений» и «диспетчер»

### 4.1 Слой намерений (расплывчатый запрос → хороший результат)
1. **Понять задачу:** тип и домен.
2. **Бриф.** Не больше 2–3 вопросов, только **кнопками с вариантами** и готовым вариантом по умолчанию. Есть кнопка «просто сделай»: тогда агент делает допущения и явно их помечает.
3. **Если пользователь не знает, чего хочет** (стиль, дизайн), агент показывает 2–3 направления с превью и даёт выбрать (паттерн moodboard).
4. **«Глубже, а не больше»** (по образцу скилла be-ambitious, MIT). Планировщик отвечает на четыре вопроса: что сделал бы профи, с каких исходников он бы начал, какие готовые методы и инструменты есть, чем проверить результат.
5. **«Поиск готового»** перед написанием своего — против изобретения велосипедов. По эксперименту E3 одно правило поднимает долю готовых решений с 67% до 94%. Плюс проверка, что пакет существует в реестре.
5a. **Схема по типу результата (E2):**
    - сайты и приложения: премиум-планировщик пишет ТЗ, дешёвый исполнитель делает — 82% побед;
    - тексты: короткий бриф или сразу делать — 70–71%.
5b. **Слой актуальных фактов:** в продуктовые задачи подставляем реальный каталог и цены (модели знают мир только на дату обучения).
5c. **Поиск готового — по реальным данным:**
    - GitHub MCP: поиск репозиториев и кода, звёзды, активность;
    - **форки**: живые форки брошенных проектов, на сколько коммитов они впереди, дата последнего push;
    - реестры npm и PyPI + deps.dev + ecosyste.ms: зависимые проекты, OpenSSF Scorecard, не заархивирован ли репозиторий;
    - проверка, что пакет существует.

    **Пользователю токен не нужен:** запросы к GitHub идут через наш бэкенд с токеном нашего GitHub App и кэшем, метаданные пакетов — из открытых API без ключа. Свой GitHub пользователь подключает только по желанию.
5d. **Дизайн-пайплайн для сайтов и приложений** (гипотеза владельца, проверяется: `research/13-design-pipeline.md`):
    1. выбор направления — мудборд и референсы, пользователь выбирает из 2–3 вариантов;
    2. `design.md`: токены, типографика, моушн;
    3. сборка премиум-моделью с дизайн-скиллами и компонентами (21st.dev, библиотеки UI), `max_tokens` на максимум;
    4. рендер → скриншоты → самокритика → доработка.

    Итоговую оценку дизайна даёт человек: модели-судьи не отличают «генерик».

    Критерии приёмки для планировщика и самокритики:
    - своя концепция и «фишка»;
    - хореография моушна;
    - нестандартная типографика;
    - запрет шаблона «градиентный hero + большая фраза + карточки со статистикой + неон».
6. **План простыми словами → выполнение → «что проверено»** человеческим языком.

### 4.1a Плейбуки: процесс «команды профессионалов» с воротами (идея владельца, 2026-10-22)
**Проблема:** модели торопятся и сразу пишут код. Владелец лечил это вручную: заставлял модель идти по шагам, как студия.

Это не велосипед, это известный подход **spec-driven development**: GitHub Spec Kit, AWS Kiro, BMAD-METHOD, obra/superpowers. Наш E2 подтверждает: на сайтах «сначала ТЗ как у профи» побеждает в 82% случаев, «сразу делать» — в 59%.

**Что берём и что меняем:**
1. **Ворота в коде, а не в промпте.** Правило «работай как команда» модель может пропустить. Харнес не даёт перейти к сборке, пока нет артефактов предыдущих этапов и они не прошли проверку. Принцип тот же, что у детерминированной безопасности.
2. **Плейбук выбирает диспетчер по типу задачи, глубина процесса зависит от задачи.**
   - Сайт, приложение, бизнес-расчёт — полный плейбук.
   - Текст — короткий бриф: тяжёлое ТЗ на текстах проигрывает (E2: 40% против 71%).
   - Мелкая правка — без плейбука.

   Внешние данные о тяжёлых процессах:
   - BMAD — долго и дорого;
   - про superpowers пишут «раздут для новых моделей»;
   - на сильных моделях пошаговое планирование экономит деньги, а не повышает точность (arXiv 2609.20804).

   Поэтому ценность ищем в этапах **решений** (что хочет человек, референсы, готовое, стек), а не в длинных списках микрозадач.
3. **Казуал не заполняет анкету.** Человеку показываем максимум 1–2 выбора: «вот что я понял — так?» и 3 мудборда. Остальное агенты решают сами и явно помечают допущения.
4. **У каждого этапа своя роль и модель** по пункту 5 «Роли моделей». Проверяет всегда не тот, кто делал (правило D7).

**Плейбук «сайт/лендинг»:**

| Этап | Артефакт | Кто | Ворота |
|---|---|---|---|
| 0. Бриф | `BRIEF.md`: для кого, цель, одна главная мысль, CTA, конкуренты, чем отличаемся | премиум-планировщик | человек подтвердил «так» (или «просто сделай») |
| 1. Исследование | `RESEARCH.md`: 5–10 референсов и конкурентов, актуальные факты (каталог и цены a6) | дешёвая модель + поиск | ссылки живые, факты с датой |
| 2. Не велосипед | `PRIOR-ART.md`: шаблоны, компоненты, библиотеки, форки | GitHub MCP + deps.dev | пакеты существуют, не заархивированы |
| 3. Направление дизайна | 3 мудборда → `DESIGN.md` (палитра, шрифты с кириллицей и лицензией, сетка, моушн, бан-лист) | премиум + человек | человек выбрал один |
| 4. Контент и структура | `CONTENT.md`: секции и тексты до вёрстки | короткий бриф → исполнитель | нет устаревших фактов, нет AI-штампов |
| 5. Стек и план | `PLAN.md`: стек, файлы, задачи, критерии приёмки | планировщик | ревью другим семейством |
| 6. Сборка | код | дешёвый исполнитель | собирается, без ошибок в консоли |
| 7. Проверка | скриншоты desktop/mobile, Impeccable detect, Lighthouse, сверка с `BRIEF`/`DESIGN`/бан-листом | ревьюер другого семейства | все проверки зелёные |
| 8. Показ | превью + «что проверено» простыми словами | — | правки человека → этап 6 |

**Итог E6:**
- Если бренд и бриф заданы, способ сборки почти не важен. Берём самый дешёвый: «сразу + 2 круга критики».
- Картинки (gpt-image) и «2 варианта → гибрид» — для выбора направления, когда стиля ещё нет.
- Критик обязан проверять смысл: дубли показателей, элементы без функции, понятность для казуала.
- **Никаких пояснений очевидного прямо в интерфейсе** (боль владельца): «Так выглядит ваш сайт» под превью, «Нажмите, чтобы открыть» под кнопкой. Подсказка допустима, только если отвечает на вопрос, который у человека реально возникнет в этом месте («Сайт пока виден только вам» отвечает на «а кто его видит?»). Не больше одной-двух подсказок на экран.

**Вариант «сначала картинка»** (идея владельца, проверен в E6): gpt-image-2.5 рисует 3 макета экрана (≈$0.001 за штуку, русский текст почти без ошибок). Человек выбирает один, модель со зрением снимает с него `DESIGN.md` и разметку, исполнитель собирает, затем скриншот сравнивается с макетом.

**Как говорим с казуалом:** ответ в 3–5 строк, как 12-летнему, без воды; подробности — по кнопке «Подробнее». Это относится и к итогам совета, и к отчётам «что проверено».

Плейбук — это маленькая программа-оркестратор поверх Pi. Готового решения нет ни в Pi, ни в dsh, ни в Harness², но есть кирпичи: пример `subagent/` в Pi (цепочки агентов на своих моделях), `plan-mode/`, хуки-блокировки; Workflows и Stop-хуки в Claude Code как образец.

**Первый реальный плейбук — `design-pipeline` владельца** (convyrtech/design-pipeline, проверен на The Raki): разбор эталона → бренд из источников → спецификация движения → 2 прототипа на выбор владельца → гейты скриптами (`flow.py`, `gate.py`) после каждой правки → судья без кода. Подключаем его как есть через AGENTS.md и адаптер для Pi.

**Что харнесс обязан делать сам** (E8b, 23.10: DeepSeek 1017 провёл design-pipeline внутри Pi до шага 7 за 11 ходов, ≈3,5 ч, ≈$1.05):
1. **Маршрут к поставщику.** У одной модели цена отличается в 100 раз, скорость — в 5 раз, всё решает кэш. Агентный цикл каждый раз шлёт весь контекст, поэтому без кэша он дорогой. Шлюз закрепляет поставщиков с кэшем, замеряет время до первого токена и уходит от медленных.
2. **Ворота держит харнесс, не агент.** Пока `flow.py` не сказал «ок», харнесс не показывает владельцу лист следующего шага и не пускает в файлы следующего шага. В E8b агент перешёл к раскадровке при незакрытом шаге 3, написал «выбор записан» и переименовал лист, чтобы пройти линтер.
3. **«Как рекомендуешь» закрывает выбор.** Это отдельный тип ответа: владелец доверил решение, и агент берёт свою рекомендацию. Нельзя переспрашивать буквами: в E8b казуала спросили трижды.
4. **Длинный ход виден.** Ходы шли 10–40 минут, а казуал видел тишину. Нужна строка прогресса («снимаю референсы, 3 из 6»), бюджет на ход и одно сообщение «работаю, будет через ~N мин».
5. **Инструмент «подагент на другой модели»** для судьи и проверки (правило D7). В E8b агент собрал его сам из `pi -p`.
6. **Песочница без секретов.** В окружении агента нет ключей; ключ к шлюзу подставляет харнесс. В E8b агент перебирал переменные окружения в поисках ключей.
7. **Проверка смысла — отдельные ворота** перед показом. Она ищет дубли показателей, элементы без функции, числа без смысла, служебные заглушки в тексте вроде «[OI]».

**Обещания и факты** (владелец 23.10: «излишняя тревога… потом приходится по 10 раз править текста на всех страницах»; «никто не будет запускать сервис с пустыми обещаниями. а если будет то ради теста маркетинга или спроса»):
- **Один файл фактов на продукт** (цены, число моделей, лимиты, что работает). Тексты страниц берут числа и обещания из него подстановкой, поэтому меняем в одном месте.
- **Пока идёт дизайн, «план» не блокирует** работу, линтер только предупреждает. Блокирующая проверка «работает ли это» — одна, перед публикацией (шаг 8).
- **Два режима страницы в паспорте:**
  - «запуск» — каждое обещание подтверждено замером до выкладки;
  - «тест спроса» — честная рамка «ранний доступ», обещания про будущий сервис, кнопка реально собирает заявки, на странице счётчик конверсии. Узнаём спрос, никого не обманывая.

Такие же плейбуки нужны для бизнес-расчёта (совет v3: вопросы → допущения в JSON → расчёт кодом → ревью → синтез) и для бота или автоматизации.

### 4.2 Диспетчер (подтверждён экспериментом E1: агенты сами находят нужный скилл в 57–64%, диспетчер — в 90–100%)
- Каскад в интерфейсе `classifier` Pi:
  1. правила;
  2. локальный поиск по названиям и описаниям (ключевые слова + эмбеддинги);
  3. вызов диспетчера: Gemini 3.8 Flash или GPT-6 Luna (быстрый режим), Qwen 3.8 Flash (JSON);
  4. если ничего не подходит — молчим.
- Backend заменяемый: Jev, Luna, локальная decision-модель.
- Дешёвая быстрая модель на старте задачи и на границах подзадач. Выбирает скиллы, тулы и MCP, модели под роли, уровень риска и решает, нужно ли уточнение.
- Основной агент видит **только выбранное**: оно дописывается в историю, кэш не ломается.
- Статистика использования: неиспользуемые скиллы предлагаем отключить.
- Пользователь не видит ни скиллов, ни моделей. Максимум переключатель «быстрее / качественнее».

### 4.3 Совет экспертов (профиль «Повседнев»)

## 6. Память (досье `research/09-memory-rag.md`)

- **v1:**
  - `MEMORY.md` и `USER.md` с лимитом, снимок фиксируется на сессию;
  - дневные заметки;
  - SQLite FTS5 (стемминг ru/en + trigram);
  - правки и удаления — через очередь подтверждения;
  - у каждой записи источник и доверие.
- **v1.x:** гибрид с `sqlite-vec` + локальная EmbeddingGemma 2 (175–314 МБ, скачивается по требованию). Затухание старых записей, MMR.
- **Код:** grep + карта репозитория (tree-sitter) + LSP. Векторный индекс кода не делаем (Cursor отказался от него в июле 2026).
- **Самообучение:**
  - факты добавляются сами;
  - скиллы-кандидаты копятся в «теневом режиме» и включаются только после одобрения пользователем или доказанной пользы в evals.

## 9. Главные риски

1. **Маркетплейс как «тихий исказитель»:** подмена моделей, скрытые промпты, игнорирование параметров, отсутствие кэша. Закрываем канарейками и закреплением поставщика.
2. **Утечка кода и секретов через анонимных поставщиков.** Закрываем вычисткой секретов и политикой «что можно отправлять».
3. **Сложность собственной платформы** (sidecar, протокол, совместимость, снапшоты, память). Закрываем этапностью и берём готовое (Pi, Graphone, OpenCode, Hermes, Codex).
4. **Дрейф моделей и поставщиков.** Нужен постоянный мониторинг, а не разовые замеры.
5. **Windows:** песочница, bash, PTY.
6. **Подпись и дистрибуция из РФ.**
