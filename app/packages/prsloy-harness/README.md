# @prsloy/harness

Расширение Pi 1.4, которое грузится в каждую сессию агента PRSLOY Desktop. Оно делает дешёвые модели
(DeepSeek V4.1 Flash, Kimi K3.1) надёжнее: всё в коде, ничего не держится только на промпте. Каждая
практика уже доказана в наших досье или экспериментах (`PLAN-alpha.md` §3); новых не придумывали.

## Подключение

```ts
import { createPrsloyHarness } from "@prsloy/harness";

new DefaultResourceLoader({
  cwd,
  agentDir,
  extensionFactories: [createPrsloyHarness({ profile: "code" })],
});
```

Ещё два способа, оба проверены интеграционным тестом:

- путь к файлу: `additionalExtensionPaths: [".../packages/prsloy-harness/src/index.ts"]` (так грузит
  `extensionPaths` дорожки ядра). Профиль тогда берётся из `PRSLOY_PROFILE` (`code` по умолчанию);
- каталог пакета: в `package.json` есть `pi.extensions`.

`register(pi)` — точка входа с настройками по умолчанию. Настройки (`HarnessOptions`) описаны в
`src/options.ts`; любую практику можно выключить через `disable`.

## Почему серверы через `&` переписываются, а не отслеживаются

Процесс из `(cmd &)` после выхода оболочки переподчиняется init: надёжно найти его потом можно только по
порту или командной строке, а это гадание (чужие процессы, тот же порт у другого сервера, разный `ps` на Linux,
macOS и Git Bash). Если запустить задачу самим через реестр, PID, порт и лог известны с первой секунды, сервер
закрывается с сессией и при падении хоста, а `pkill` по нему превращается в точную остановку. Переписывается
только то, что разобрано уверенно: кавычки и скобки сходятся, `cd` перед задачей без переменных, задача похожа
на сервер (`looksLikeServer` или `node server.js`, `python app.py` и т. п.). Остальное — `sleep 1 & sleep 2 &
wait`, сборки, циклы — выполняется как написано.

Почему `pkill -f` убивал сам себя: Pi запускает команду как `bash -c "<команда>"`, и шаблон из команды есть
в командной строке этого bash. Pi ставит bash в отдельную группу процессов, поэтому безопасная замена
(`__prsloy_pkill`) пропускает процессы своей группы: сервер, запущенный прошлым вызовом, — в чужой группе
и будет убит, а свой shell — нет. На Windows групп нет, поэтому там `pkill -f` блокируется с подсказкой
`process action=stop port=…`.

## Почему прокси отдаёт поток вживую, а a6proxy копил целиком

a6proxy копит ответ целиком: дизайн-прогону всё равно, когда придут токены, зато любой обрыв можно повторить.
Чату нужны токены по мере появления. Поэтому граница одна — первый полезный кусок: до него агент ничего не
получил, кроме `: ping`, и любой сбой повторяется незаметно; после — повтор сломал бы поток у Pi (E9, баг 1),
и вместо него приходит одна честная ошибка, по которой UI показывает «Связь с моделью оборвалась» и «Повторить».

## Порядок обработчиков

`tool_call`: бюджет → петли → таймаут bash (первый блок останавливает цепочку, поэтому сервер не запустится,
если бюджет исчерпан). `tool_result` идёт цепочкой в порядке установки: петли → таймаут → вывод → правки → проверка синтаксиса →
предупреждение бюджета → секреты. Пути файлов разрешаются как в Pi (`src/paths.ts`: `@`, `~`, `/c/…` Git Bash на Windows).

## Замер на казуальных задачах

`bench/tasks/` — 8 задач обычного человека, у каждой проверка кодом (`check.mjs`) и заготовка решения для
фейковой модели (`fake.json`): сайт-визитка с формой (страница в Chromium без ошибок, форма с полем и кнопкой),
CSV → сводка по месяцам (верные суммы), Telegram-бот (без сети: обработчик `/start`, синтаксис, токен не в коде,
зависимости записаны), «почини чужой код» (тест зелёный, сам тест не тронут), «разберись в проекте» (три факта
из кода в ответе), змейка на canvas (без ошибок после нажатия стрелок), Python → JavaScript (тот же вывод),
«сделай быстрее» (тот же вывод, минимум вдвое быстрее — замер до и после на той же машине).

`scripts/bench.mts` гоняет задачи через тот же рантайм, что агент-хост приложения (`createPixRuntime` +
граница записи + харнесс; `--harness off` — граница записи и тот же системный промпт без практик), и пишет на
задачу: успех проверки, время, вызовы, деньги (стоимость сессии из usage, с ревью), вмешательства харнесса
(петля, таймаут, сервер в фон, стоп-гейт, ревью, утечка разметки, бюджет, ремонт аргументов, ошибки проверки
аргументов, вопросы «менять вне проекта?»). Итог — `bench-*.md` и `bench-*.json`. Ключ — только из окружения.

```sh
node packages/prsloy-harness/scripts/bench.mts --fake                     # без ключа, как в CI
PRSLOY_GATEWAY_KEY=… node packages/prsloy-harness/scripts/bench.mts --harness on  --model prsloy/kimi-k3.1-pro
PRSLOY_GATEWAY_KEY=… node packages/prsloy-harness/scripts/bench.mts --harness off --model prsloy/kimi-k3.1-pro
```

Страницы проверяются в Chromium Playwright (свой, `BENCH_CHROMIUM` или `/opt/pw-browsers/chromium`); нет
браузера — проверка «не выполнена», а не провалена.

### Второе мнение по целой ветке

`review-live.mts` проверяет самого проверяющего на синтетических диффах. Когда ветку писал агент и живого
человека-ревьюера нет, тот же путь (прокси надёжности, промпт `reviewPrompt`, разбор `parseVerdict` с
цитатой из диффа) запускается по настоящему диффу ветки:

```sh
PRSLOY_GATEWAY_KEY=… node packages/prsloy-harness/scripts/review-branch.mts \
  --base 6c95a70 --task "что просил пользователь" --checks "итог проверок"
```

`--path` сужает дифф (большой дифф обрезается и теряет файлы), `--limit` поднимает потолок символов,
`--reviewer` задаёт проверяющего вместо пары к писателю. Выход 0 — PASS, 4 — FAIL с замечаниями, 3 — шлюз
ответил 402. Разбор с токенами и ценой пишется в `--out` (по умолчанию `review-branch.json`).
