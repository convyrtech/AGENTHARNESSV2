Прогон CI на `desktop/ci` @ 1febe3c: https://github.com/convyrtech/AGENTHARNESSV2/actions/runs/40184349436.

- Красная она ровно по 6 настоящим багам ниже: 566 нарушений по матрице, ещё 3736 в baseline. Цифры совпадают с
  локальным прогоном до точки. Так и задумано, пока ui и features их не починят.

### 1. Что проверяется

- `e2e-audit/layout-lint.spec.ts` проходит ключевые экраны с фейковым шлюзом. Два запуска приложения на каждую пару
  «масштаб + тема»:
  - **«Код»** — путь casual-audit:
    - первый запуск: ключ, неверный ключ, папка;
    - пустой чат, ход, превью;
    - диалог отката и результат отката;
    - ошибки модели: деньги, ключ, обрыв, модель нет;
    - карточка «Модель сбилась»;
    - «Дизайн» без сборки;
    - все вкладки настроек.
  - **«Дизайн»** публичной сборки: без инструментов → инструменты из zip → пустой → ход с карточкой и тремя видео
    кандидатов.
- **Матрица:**
  - окна 800×600, 1024×768, 1280×720, 1366×768, 1440×900, 1920×1080, 2560×1440 при 100 % и 150 %;
  - 1280×720 и 1366×768 ещё при 125 % и 175 %;
  - светлая и тёмная тема.
    Масштаб — `--force-device-scale-factor`. Окно — физические пиксели, контент получает size / scale CSS px. Ниже
    минимума (760×480) окно держит минимум, и это помечается в отчёте.
- Правила — код в странице, пакет `app/packages/layout-rules` (`@zeno/layout-rules`). Пакет без зависимостей и общий
  с harness: harness отправляет `lintLayout.toString()` в страницы, которые агент строит пользователю.
  `test/self-contained.test.ts` запускает функцию из её исходного текста в чистом `node:vm`-контексте. Правила, по
  одному нарушению на элемент:
  - `root-hscroll`: у корня есть горизонтальная прокрутка;
  - `off-window`: элемент вылезает за окно, и никакой предок его не обрезает и не прокручивает;
  - `text-clipped`: текст обрезан своей коробкой или скрывающим предком. Исключения: намеренный ellipsis, line-clamp
    и `data-clamp`; прокручиваемые контейнеры и visually-hidden 1×1 не в счёт;
  - `overlap`: пересекаются видимые прямоугольники button / a / input / [role=button]. Видимость: клик в центр или в
    углы попадает в элемент; кнопки под модалкой не в счёт;
  - `target-size`: меньше 24×24 CSS px; ссылки внутри предложения не в счёт (WCAG 2.5.8);
  - `small-text`: шрифт меньше 11 px;
  - `focus-hidden`: фокус с клавиатуры (`focus({focusVisible:true})` после нажатия клавиши) не меняет вид элемента и
    четырёх его предков (outline, box-shadow, border, фон, цвет). Проверяется раз на экран, при 1366×768;
  - `window-min`: окно меньше своего минимума.

Новый job `plan` (ubuntu) решает, что это за прогон, и отдаёт `mode/version/tag/publish`.

- **Run workflow на `main` с `version`:**

  GitHub («Triggering a workflow from a workflow»): «events triggered by the GITHUB_TOKEN, with the exception of
  workflow_dispatch and repository_dispatch, will not create a new workflow run». `push` тега и `release: published`
  сюда входят. Защиты сверх этого не нужно. На случай, если кто-то сменит токен на PAT, она всё равно есть: `plan`

### 2. Старые пути

- **`push` тега `v*`:**
  - если релиза ещё нет — `tag-release`: сборка → проверки → релиз с файлами (как раньше);
  - если релиз уже есть (тег создал UI-релиз) — `skip`: файлы прикрепляет прогон `release: published`;
  - `concurrency.group` теперь включает `event_name`, поэтому два прогона одного UI-релиза друг друга не отменяют.
- **`release: published` (UI):**
  - в summary стоит предупреждение (и `::warning`): «Обновления у пользователей не работают, пока этот прогон не
    прикрепит файлы»;
  - если прогон упал, job `unpublish` (`always()`, если `release` не `success`) проверяет ассеты. Если `latest.yml`
    нет, он вызывает `gh api -X PATCH …/releases/<id> -F draft=true`. Тогда релиз уходит из `releases.atom` и не
    держит обновления;
  - флаг `-F`, а не `-f`: `-F` шлёт JSON `true`, а `-f` — строку `"true"`.
  - Права: у job стоит `permissions: contents: write`. По документации REST «Update a release» этого достаточно для
    fine-grained/GITHUB_TOKEN: «Contents» repository permissions (write).
- Тег не semver с «v» → `plan` падает с понятной ошибкой. Для UI-релиза это тоже ведёт в `unpublish`.

  - каналы, URL загрузки и диапазоны остаются кодом `GitHubProvider`.
- `auto-update.ts`: реальный путь `load()` ставит этот провайдер. Фид прежний: `convyrtech/AGENTHARNESSV2`,
  prerelease; петлевой host только под `PRSLOY_E2E=1`.
- Юнит-тесты `update-provider.test.ts`:
  - откат к новейшему полному релизу;
  - полный первый релиз (один запрос atom);
  - ограниченный отказ;
  - чужие ошибки не глотаются.

**Баг 1. Распаковка Node/Python ломается на пути не из ANSI-кодировки.**

- `runtime-provision.ts` вызывает `C:\Windows\System32\tar.exe` (bsdtar). Тот гонит аргументы через ANSI-кодовую
  страницу.
- Проба (`tar-probe.json`, тот же `execFileSync`) на раннере с ACP 1252 / OEM 437 (`codepage.json`):
  - кириллица в пути архива → `tar.exe: Error opening archive: Failed to open 'C:\Users\???? ??????\…'`;
  - кириллица в `-C` → `could not chdir to 'C:\Users\???? ??????\…'`;
  - кириллица в относительном пути тоже ломается; проходит только ASCII → ASCII.
- Последствие: у пользователя нет бандлового Node и Python. Агент молча берёт системные (если они есть), а
  «Дизайн» лишается своего Python.
- Кого задевает. На русской Windows ACP = 1251, кириллица в ней есть, так что «Иван Петров» на русской
  Windows, скорее всего, пройдёт. Проверить в Actions нельзя: смена системной локали требует перезагрузки.
  Ломается кириллический профиль на Windows с английской/иной системной локалью и любые символы вне 1251.
- Предложение: распаковывать в Node без внешнего `tar.exe`. Например, пакет `tar` (node-tar), чистый JS: пути
  идут через Unicode-API Node. Обойти через ASCII-временную папку нельзя: TEMP у такого пользователя тоже
  кириллический.

**Баг 2. Python в bash агента пишет в ANSI-кодировке.**

- `python3 -c "print('привет')"` через шим core в бандловый Python, в обычном ASCII-профиле, падает:
  `UnicodeEncodeError: 'charmap' codec can't encode characters … cp1252.py`. Под кириллическим профилем, где
  бандлового Python нет, так же падает системный.
- На русской Windows (cp1251) вместо падения будут кракозябры: Pi читает вывод как UTF-8.
- Окружение «Дизайна» (`design/env.ts`) уже ставит `PYTHONUTF8=1` и `PYTHONIOENCODING=utf-8`, окружение агента
  (`prsloy/agent-env.ts`) — нет.
- Предложение: те же две переменные в env Agent Host.

## Bash-тул Pi на Windows

**Какой shell берёт Pi** (`pi-coding-agent/dist/utils/shell.js`, `getShellConfig`):

2. `%ProgramFiles%\Git\bin\bash.exe`, затем `%ProgramFiles(x86)%\Git\bin\bash.exe`;
3. `where bash.exe` по PATH. Вызов: `bash -c <command>`; для `System32\bash.exe` (WSL) — `-s` через stdin.

**Что показал smoke на базе Zeno, до правки core:**

- Раннер как есть (Git for Windows стоит): работает, Git Bash (MSYS2) `/usr/bin/bash`.
- Чистая Windows (Git спрятан: `ProgramFiles*` → пустая папка, из PATH убраны git/msys/cygwin): **не работает**,

  Приложение не падает: карточка тула красная, ход завершается.
- Ловушка WSL: когда bash.exe ищется по PATH, находится `C:\Windows\System32\bash.exe` — лаунчер WSL. Тул
  отвечает `Windows Subsystem for Linux has no installed distributions…` в UTF-16 (мусор `W\0i\0n\0…`), exit 1.
- Кандидаты (Git спрятан, Pi направлен на shell через `shellPath`):

| Кандидат                | Размер (архив / распак.) | Результат                                                                                                                                                                  |
