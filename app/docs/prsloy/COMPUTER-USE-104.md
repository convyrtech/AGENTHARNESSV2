# Компьютерное управление: прототип #104

Статус: исследовательский opt-in, не включён в alpha 5.

Актуальный статус и доказательства проверок приведены в `COMPUTER-USE-104-PLAN.md`. Текущий Munim runtime использует обёртки `munim_list_apps`, `munim_get_app_state`, `munim_type_text`, `munim_click`, `munim_screenshot`, токены поколений и общий durable recovery. Снимок должен подтвердить PID, одно окно и корректный идентификатор окна до выдачи токенов; выбор Munim остаётся PID-only и точное системное закрепление HWND не гарантируется. Действия Munim требуют решения владельца после неопределённого результата. При запуске отключается старая PRSLOY-owned запись Munim в общем MCP-конфиге; пользовательские записи сохраняются. Уже работающая старая версия процесса без общего журнала всё ещё может обойти блокировку, поэтому безопасное сосуществование версий не доказано. Общий `pnpm test` локально в Windows остаётся красным; Windows CI для `f6d169a` прошёл, но не запускает packaged Cua/Munim E2E и не проверял последующие изменения.

## Cua backend: эксперимент

После сравнения на одном Windows fixture добавлен альтернативный backend Cua Driver 0.38.0. Он не входит в комплект приложения и не устанавливается автоматически. Для проверки нужен весь отдельно проверенный portable-комплект Cua; укажите абсолютный путь к его `cua-driver.exe` и до запуска PRSLOY задайте в окружении процесса:

```powershell
$env:PRSLOY_COMPUTER_USE = "1"
$env:PRSLOY_CUA_BINARY = "C:\Tools\cua-driver\cua-driver.exe"
```

Если указаны оба бинарника, выбирается Cua. Без opt-in computer-use не включается. Cua запускается отдельным `mcp --direct`, а модель получает ограниченные обёртки с PID, HWND и токенами снимка. На native fixture проверены точное окно, устаревший токен, ввод и подтверждение результата; статус packaged E2E фиксируется отдельно.

**Граница безопасности:** этот путь не является ОС-песочницей, обычный shell в агенте остаётся отдельным каналом. Перед действием Cua записывается намерение в общий SQLite-журнал профиля. Ввод с подтверждённым чтением значения может завершиться без ручного решения; требуется новый снимок. Клик и неопределённый результат, включая Stop или потерю хоста, блокируют последующие действия до явного решения владельца; чтение окна разрешено. Остановка не откатывает действие, которое может выполниться позже. Подтверждение значения и решение владельца не доказывают конечный бизнес-результат в другом приложении.

## Что добавлено

- `apps/desktop/src/main/prsloy/computer-use.ts` формирует MCP entry для Munim Computer Use `0.9.0`.
- По умолчанию сервер не добавляется в профиль и не запускается. Вариант с `npx` явно помечен как developer-only; для повторяемого теста предпочтителен заранее выданный путь к `munim-computer-use.exe`.
- `scripts/computer-use-probe.mjs` проверяет только MCP `initialize` и `tools/list`. Он не скачивает пакет, не перечисляет окна и не выполняет действия.

## Исторический контракт первого vertical slice

Следующий раздел описывает раннюю реализацию, а не текущий runtime.

1. `list_apps` — агент получает список окон и выбирает конкретный PID; неоднозначное имя не угадывается.
2. `get_app_state` — читает UI Automation tree выбранного приложения.
3. `click` или `type_text` — действие только по свежему element id.
4. После действия — отдельный свежий `get_app_state`. `return_state` Munim может приложить состояние, но guard требует отдельного чтения.
5. `screenshot` — fallback только для интерфейса без доступного дерева; картинка должна пройти через модель с явным `input: ["text", "image"]`.

Отмена остаётся на существующем `zeno:agent:abort`; сигнал отмены не гарантирует остановку или откат внешнего действия. Не следует заявлять успех, если повторное чтение не подтверждает конечное состояние.

## Безопасная проверка на Windows

Тестировать только в отдельной сессии Windows и с искусственным приложением/папкой:

```powershell
node app/scripts/computer-use-probe.mjs C:\Tools\munim-computer-use.exe
```

После canary оператор вручную запускает отдельное тестовое приложение и выполняет сценарии:

- открыть приложение и выбрать его по `list_apps`;
- прочитать поле/кнопку через `get_app_state`;
- ввести маркер `PRSLOY-104` и нажать кнопку;
- повторно прочитать состояние и проверить, что маркер отображён/файл создан в тестовой папке;
- закрыть/изменить окно между наблюдением и действием: ожидать ошибку или новый `get_app_state`, но не старый клик;
- нажать «Остановить» во время ожидания: ожидать `aborted`, без сообщения об успехе;
- передать искусственный screenshot через реальный шлюз и зафиксировать, дошла ли `image_url`.

## Фактический запуск (2026-10-30)

- Munim Computer Use `0.9.0` запущен напрямую из временной папки, без установки. SHA-256 ZIP совпал с GitHub Release: `2997b50ca97c5161780c5d8cd8821045588c88300b6786879d224adfe8956984`. Бинарник upstream unsigned (`Get-AuthenticodeSignature: NotSigned`).
- Искусственный WinForms fixture собран локальным .NET SDK 9.0.203 и запущен с уникальным заголовком `PRSLOY 104 Test Fixture`; PID в последнем успешном запуске — 20484. Тестовая папка: `%LOCALAPPDATA%\Temp\opencode\munim-104\test-output`.
- Реальный MCP `initialize` вернул `mt-desktop`, версию `0.9.0`; `tools/list` вернул 19 инструментов, включая `list_apps`, `get_app_state`, `type_text`, `click`, `set_value`, `screenshot`.
- `list_apps` нашёл fixture по PID; `get_app_state` прочитал только одну форму: поле `e2`, кнопка `e3`.
- Действия по элементам с `return_state: true` завершились: `type_text` ввёл `PRSLOY-104-MARKER`, свежий UIA state показал текст в поле, `click` по свежему `e3` обновил статус на `Saved: PRSLOY-104-MARKER`. Файл `result.txt` содержит ровно `PRSLOY-104-MARKER`.
- `screenshot` вернул реальный MCP image-content `image/png` размером 21 383 байта. Это подтверждает доставку изображения backend → MCP-клиент, но не передачу через PRSLOY gateway → модель.
- `click` по перекрытому элементу вернул отказ «covered by another window»; `Ctrl+A` отказал из-за текущей раскладки. Позже элементный `type_text` и `click` прошли в фоне. `set_value` оставлял старый префикс курсора, поэтому для точного ввода использован выделенный тестовый путь через `type_text`.
- Ошибка fixture после преждевременного тестового клика была диагностирована: тестовый аргумент указывал на каталог вместо файла; после передачи конкретного `result.txt` сценарий прошёл.
- Ошибка по несуществующему element id `e999999` честно вернула «not in current snapshot». На вызове `wait(10s)` завершение дочернего backend-процесса прервало ожидание; это проверяет остановку backend, но не полноценный UI `agent.abort` в PRSLOY.
- До исправления upstream платные модельные прогоны не выполнялись: `/v1/models` был доступен, а chat возвращал 301/307.

## Канал PRSLOY и image-canary (2026-10-30)

- Через read-only аудит найден устаревший upstream-адрес активного канала; он возвращал HTTP redirect вместо API-ответа.
- После явного согласования изменён только upstream-адрес этого канала. Другие поля, каналы и контейнеры не менялись.
- Текстовый smoke после изменения: DeepSeek `deepseek-v4.1-flash-1017`, HTTP 200, usage 37 input + 1 output token при `max_tokens=1`.
- Одинаковый image-canary отправил 1x1 PNG через реальный `image_url` в `POST /v1/chat/completions`:
  - `deepseek-v4.1-flash-1017`: HTTP 200, 236 prompt + 128 completion tokens; изображение было обработано, но весь лимит `max_tokens=16` ушёл на reasoning, финальный ответ отсутствует (`finish_reason=length`).
  - `gpt-6.1-terra`: HTTP 200, ответ `IMAGE_OK`, 323 prompt + 38 completion tokens, из них 30 reasoning и 0 cached.
- Расчёт по опубликованному `/api/pricing` и `billing_expr`: DeepSeek ≈ `0.00077024 ₽`, GPT-6.1 Terra ≈ `0.007733 ₽`, всего ≈ `0.00850324 ₽`. Это расчётная стоимость по usage и тарифной формуле; шлюз не прислал отдельное поле ruble cost.
- Латентность в этом запуске не фиксировалась корректно: оболочка дождалась ответа файлов, но завершилась по собственному таймауту 180 с. Повторные запросы не выполнялись.
- Image-channel теперь подтверждён end-to-end: локальный PNG → PRSLOY gateway → выбранная модель → completion. До смены upstream это было непроверяемо из-за 301.
- `corepack pnpm ... test` не дошёл до тестов: отсутствуют зависимости и команда пыталась вызвать `pnpm install`; Node 22.16.0 ниже заявленного `>=22.19.0`.

Итог: реальный backend проверен на искусственном Windows-приложении для наблюдения, элементного ввода, клика, повторного наблюдения, screenshot, stale-id ошибки и принудительной остановки backend. Сравнение моделей и end-to-end cancellation через PRSLOY UI остаются непроверенными.

## Историческая интеграция в agent loop (opt-in)

Ранняя версия использовала `computer-use.ts` и прямые вызовы Munim. Она заменена: актуальные ограничения инструментов, opaque ID, durable recovery и результаты проверок описаны в начале этого документа и в `COMPUTER-USE-104-PLAN.md`. Исторические результаты выше относятся только к указанным в них сборкам и не подтверждают готовность текущей версии.
