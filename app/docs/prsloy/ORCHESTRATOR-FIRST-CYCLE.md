# Первый рабочий цикл #103

Решение владельца 2026-11-10: разработка через опубликованную alpha.5; учитывать
все оплаченные попытки и каждое вмешательство ведущего с причиной. Ветка
`work/103-first-cycle`, база `9349326`.

Готово означает: включаемый явно инструмент делегирования в настоящем приложении
создаёт отдельного исполнителя, проверяет изменённые файлы командой из исходного
задания, отправляет конечный diff и результаты модели другого семейства и возвращает
короткий итог. Заявление исполнителя не заменяет факты среды.

Первый исполнитель работает только с явно выбранными файлами через штатные
read/edit/write. Команду проверки запускает ведущий через обычный
`ExtensionToolContext.executeTool('bash', ...)`, с hooks и разрешениями. Это
первый ограниченный цикл; общий bash/MCP и параллельные исполнители — после проверки.

Контекст и разрешения исполнителя создаются заново. Общие skills, extensions,
настройки, переписка ведущего и рекурсивное делегирование не наследуются. Секреты
не копируются; используется доступ к моделям существующего runtime.

Отмена, лимит расходов с резервом на ревью, неизвестное списание, невалидное ревью,
одинаковое семейство и изменение diff после ревью не должны давать «проверено».
Расчёт по каталогу моделей отделён от фактического списания PRSLOY на внешнем стенде.

Проверки: реальный Pi SDK с локальным фейковым шлюзом; успех, отказ/ненулевой exit,
отмена, отсутствие общих ресурсов, лимит до HTTP, невалидное ревью, изменённый diff.
Затем живой прогон через приложение на небольшой реальной задаче; модели, расходы,
ошибки и вмешательства — в DIARY и issue. `pnpm check`, `pnpm test`, desktop-ci и
независимое ревью перед слиянием. Модель по умолчанию и существующие режимы не меняем.

Порядок: чистый контракт → host/runtime и подключение → проверки SDK/UI → живой
цикл и сравнение с одним агентом. Не объявлять контракт или мок готовым оркестратором.

## Состояние 2026-11-10

Прототип подключён к Agent Host и выключен по умолчанию (`delegate: false`). Для
локального пилота в `prsloy-harness.json` ставится `delegate: true`; инструмент
принимает `task`, `paths`, `check`, `workerModel`, `reviewerModel`. Поддерживается
OpenAI-compatible API. Исполнитель получает максимум 12 запросов и 8192 выходных
токенов на ответ. Это ограничение контекста и доступных инструментов, не OS sandbox.

Контрольная команда проходит штатные hooks/permissions родителя. Полный ответ и
diff сохраняются в отдельном файле журнала; в контекст родителя идут статус,
файлы, проверка, до трёх коротких замечаний и расходы. Проверяющий видит фактический
diff и код выхода, а не пересказ исполнителя. Неизвестные списания удерживают резерв.

Оркестратор требует от исполнителя непустой итог в штатно завершённом ответе.
Если итог пуст или ответ оборван по лимиту, цикл возвращает `failed`, сохраняет
файлы и расходы, а проверку и ревью пропускает. Если ответ проверяющего оборван,
цикл возвращает `unverified`, даже когда уже полученная часть содержит JSON
с `PASS`. Все три случая проверены через настоящий Pi SDK и локальный тестовый
шлюз. До исправления каждый случай ошибочно возвращал `verified`.
Если исполнитель закончил без изменения выбранных файлов, цикл возвращает
`unverified` с этой причиной и не запускает команду проверки или ревью.

Успешно проверен SDK-цикл с локальным тестовым шлюзом: запись файла, вложенная
команда через hooks, отдельная модель проверки, компактный итог. Также проверены
отказ команды, ненулевой exit, ошибочный JSON ревью, изоляция ресурсов, отмена,
ограничение запросов, ссылки на файлы и запрет запроса до HTTP при нехватке бюджета.
Это проверка реализации, а не доказательство качества живых моделей.

Две попытки написания компонента через опубликованную alpha.5 (Kimi и MiniMax)
остановились первым HTTP 503 до ответа модели. Списания PRSLOY в обоих случаях
0 ₽, активных резервов нет. Установлен внешний блокер проверки бюджета сервиса;
повторять генерации до его устранения нельзя. Поэтому текущий прототип написан
ведущим и вспомогательными агентами, не моделями внутри alpha.5.

На `0847168` desktop-ci зелёный. Живой цикл описан ниже. Сравнение с одиночным
агентом при одинаковых условиях и выпуск нового установщика остаются отдельными шагами.

## Первый эксперимент с обучением на ошибках

В живом прогоне `0847168` MiniMax → Kimi → MiniMax дошёл до правки, теста
и независимого ревью за 235 с и 0,855 ₽. Первый вызов делегирования остановился
после чтения файла проверки вне области исполнителя. Два следующих вызова
отклонены из-за абсолютного пути и префикса `./`. Четвёртый вернул `verified`.
Это исходное наблюдение для гипотезы, качество обучения пока не измерялось.

Гипотеза: если при отказе ведущий получает код причины и один конкретный способ
исправить запрос, он реже повторяет отказ. Первые два сигнала — неверный формат
пути и выход исполнителя за разрешённые файлы. В `task` остаётся правка, в `check`
остаётся команда для ведущего. Граница файлов сохраняется. Источник истины для
результата — журнал вызовов, команда и ревью. Самооценку модели не учитываем.

Для личных уроков используем существующие `learning-log.ts` и `lessons.ts`.
Храним код причины, модель, этап и результат без исходного текста и путей.
Один короткий совет выдаётся только при совпадении события. Для общих улучшений
используем офлайн Propose–Probe–Compose из [#33](https://github.com/convyrtech/AGENTHARNESSV2/issues/33):
локальное наблюдение → кандидат → сравнение на заранее отложенных задачах → PR.
Границы доступа остаются частью кода приложения.

Сравниваем базу и кандидат на одних моделях и при одном бюджете, в изолированных
профилях. Долю циклов с `verified` и число запрещённых операций берём из фактов
среды. Считаем число отклонённых вызовов, реальные ₽, время и вмешательства до
первого `verified`. Порог пробы — меньше повторных отказов без снижения доли
`verified`, роста медианного расхода или новых нарушений границ. Один прогон
годится как пример сбоя. Результат на новых задачах нужен для принятия урока.

Протокол первой пробы: два новых изменения на копии `text.ts` — плейсхолдер
для нечисловой длительности и подсчёт строк с CR. В первом сценарии исходный
вызов использует `./text.ts`, во втором поручение просит исполнителя прочитать
проверку за пределами его файлов. Каждую задачу запускаем дважды на одном
бинарнике с одинаковым запросом, свежим профилем и одним различием — флагом
`lessons`. Порядок: путь без/с уроком, тест с/без урока. Первый заданный отказ
показываем отдельно от повторов. Случай, где целевой отказ не случился, не
доказывает эффект урока. Принимаем `verified` из результата `delegate`, а
списания из журнала PRSLOY; слова ведущего используем только для анализа UI.
